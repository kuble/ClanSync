# 가입·로그인·서비스 진입 화면 재설계안

작성일: 2026-10-24 · 상태: **변경 기획 + 화면별 상세 설계 작성 / 검토용 제안 / 구현 전**

대상: 랜딩, 회원가입, 로그인, 게임 선택, **게임 인증·재연동**, 클랜 가입의 여섯 화면. 이메일 확인 안내·클랜 생성·리더 환영까지 연결 흐름을 상세화한다.

참조: [페이지 구조](pages.md) · [클랜 홈](pages/07-MainClan.md) · [프로필](pages/14-Profile-Customization.md) · [취향 진열장 기획](profile-showcase.md)

**문서 흐름:** 이 문서의 변경 방향 → [공통 상세 설계와 화면별 목차](../02-design/entry-experience/README.md) → 각 화면의 구도·요소·문구·상태·데이터·완료 조건 → 구현 의존성 확인 → QA 구현·검증 기록. 현재는 상세 설계까지이며 앱 적용 상태와 구분한다.

## 1. 제안의 중심

**클랜 화면의 ‘함께하는 활동’과 프로필의 ‘게임별 정체성’을 서비스 입구부터 보여준다.** 같은 배경·표면·글꼴·버튼을 사용하고, 각 화면의 주요 행동을 하나씩 분명히 한다. 랜딩은 서비스 이해, 가입·로그인은 계정 진입, 게임 선택은 활동 재개, 게임 인증은 게임별 연결, 클랜 가입은 비교와 신청에 집중한다.

| 화면 | 바꿀 구도 | 가장 중요한 행동 | 줄이거나 없앨 요소 |
| --- | --- | --- | --- |
| 랜딩 | 한국어 소개 + 실제 서비스 장면의 2열 → 사용 장면 3개 → 지원 상태 → 시작하기 | 무료로 시작하기 | 첫 화면의 과도한 여백, 큰 영어 슬로건, 로그인·가입 동등 강조, 기능 캐러셀, 큰 미출시 요금표 |
| 로그인 | 공통 헤더 + 좁고 선명한 폼 + 작은 서비스 맥락 패널 | 로그인 | 화면 절반을 채운 반복 홍보문, 미구현 소셜·복구 버튼 |
| 회원가입 | 로그인과 같은 외곽 + 계정 정보 → 부가 정보 → 필수 동의 | 계정 만들기 | 오버워치만 전제한 안내, 선택 정보의 과한 강조, 추가 닉네임·꾸미기 설정 |
| 게임 선택 | 이용 중인 게임 우선 + 상태와 목적지가 보이는 카드 | 클랜으로 이동 / 신청 확인 / 연결 계속 | 큰 이모지 썸네일, 항상 노출되는 검색, 출시 예정 게임의 대형 카드 |
| 게임 인증·재연동 | 게임 정체성 + 연결 이유·제공 상태 + 한 가지 연결 행동 | 게임 계정 연결 / 다시 연결 | 과한 카드 중첩, 이름만 쓰는 ID 설명, 취소 시 인증 반복, QA와 실제 연동의 혼동 |
| 클랜 가입 | 검색·목록 + 선택 클랜 상세의 2열, 모바일은 목록 → 상세 | 소개·규칙 확인 후 가입 신청 | 가입/생성 동등 탭, 중복 신청 대기 영역, 상세를 닫아야 신청하는 구조, Premium 중심 표시 |

이번 문서는 디자인·동선 제안이다. 기존 인증·소속 정책을 변경하거나 아래 제안을 확정 요구로 승격한 상태가 아니다.

## 3. 공통 디자인 기준

### 가져올 것

- 기존 Pretendard와 `background / surface / card / border / primary / muted-foreground` 토큰을 사용한다. 다크와 라이트를 함께 설계한다.
- 클랜·프로필처럼 헤더 높이 60px, 본문 최대 폭 1280px를 공통 기준으로 삼는다. 인증 폼은 별도로 좁힌다.
- 클랜 아이콘·게임 로고 → 제목 → 판단에 필요한 정보 → 행동 순서를 유지한다. 프로필처럼 정보군을 제목·여백·구분선으로 나누고 카드 안에 카드를 계속 쌓지 않는다.
- 초록은 주요 행동과 현재 선택에 사용한다. 상태는 문구·아이콘을 함께 쓰고 색 점만으로 구분하지 않는다.
- 일반 표면 모서리는 12~16px, 큰 배너는 20px, 카드 내부 여백은 20~24px를 출발점으로 삼는다. 기존 컴포넌트 규격이 있으면 이를 우선한다.

### 입구에서 제외할 것

- 클랜 전용 사이드바, 관리 메뉴, 코인 잔액, 상점, 활동 통계판을 가입 전에 붙이지 않는다.
- 모든 화면에 큰 배너·영어 태그·슬로건을 반복하지 않는다. 인증 폼 주변에는 별도 판촉 카드와 배지 진열을 늘리지 않는다.
- 프로필의 3D 미니룸이나 취향 진열장을 진입 화면에서 직접 구동하지 않는다. 프로필 장면이 필요하면 정적인 이미지 일부를 사용한다.
- 2026-10-26 사용자 요청으로 진열장 기능은 제거됐다. 진입 화면의 미리보기·개발 범위에 포함하지 않는다.

### 크기·반응형 초안

| 항목 | 데스크톱 | 모바일 |
| --- | --- | --- |
| 본문 | 최대 1280px, 좌우 24~32px | 좌우 16px, 320px부터 가로 넘침 없음 |
| 제목 | 페이지 28~32px, 랜딩 첫 제목 40~48px | 페이지 24~28px, 랜딩 30~36px |
| 인증 | 전체 구성 최대 약 1040px, 폼 400~440px | 최대 440px의 1열, 별도 소개 패널 숨김 |
| 2열 전환 | 1024px 이상에서 랜딩·클랜 상세를 2열로 배치 | 미만에서는 순서가 명확한 1열/상세 화면 |
| 입력·조작 | 입력 글자 16px, 명확한 초점 표시 | 주요 조작 영역 최소 44px, 긴 ID 줄바꿈 |

치수는 구현 시 조정할 기준안이다. 새 화면의 접근성 수치 검증을 완료했다는 뜻은 아니다.

## 4. 전체 진입 흐름

```text
랜딩 → 회원가입 또는 로그인 → 게임 선택
                                ├─ 인증됨 + 소속 있음 → 내 클랜
                                ├─ 인증됨 + 신청 중   → 현재 신청 + 클랜 탐색
                                ├─ 인증됨 + 미소속    → 클랜 탐색
                                └─ 인증 필요          → 게임 계정 연동 → 상태에 맞는 목적지

클랜 탐색 → 소개·규칙·모집 조건 → 메시지(선택) → 신청 → 승인 대기
           └─ 클랜 만들기 → 기존 생성 폼 → 리더 환영/Discord 안내
```

- 계정 생성과 게임 계정 연동을 다른 단계로 설명한다. 게임 ID를 ClanSync 로그인 정보처럼 받지 않는다.
- 보호된 링크에서 왔다면 검증된 `next`와 기존 클랜 복귀 정보를 유지한다. 로그인·회원가입 사이를 이동해도 목적지를 잃지 않는다.
- 로그인한 사용자의 `/` → `/games`, 로고의 `/?from=logo` 예외를 유지한다. 로고로 랜딩을 볼 때는 CTA를 `게임 선택으로`로 바꾸는 안을 권장한다.
- 클랜 가입 목록은 현재 로그인 + 게임 인증이 필요하다. 비회원 둘러보기나 게임 연동 건너뛰기는 이번 안에 포함하지 않는다.
- `/profile`은 게임·클랜 가입 없이도 갈 수 있다. 온보딩을 완료해야 프로필에 접근할 수 있는 구조로 바꾸지 않는다.

## 5. 랜딩

### 구도와 정보 순서

```text
[로고]               서비스 화면 · 지원 게임            [테마] [로그인]

[우리 클랜의 다음 경기부터,]       [최신 클랜 홈 대표 장면]
[함께한 기록까지.]               [공지·일정·클랜 정체성이 읽히는 크기]
 내전 준비와 일정, 경기 기록을
 클랜원들과 한곳에서 이어가세요.
 [무료로 시작하기]  서비스 화면 보기 ↓

[함께 준비하기]      [함께 기록하기]      [나를 보여주기]
 내전·일정 장면       경기 기록 장면       게임 ID·소개·엠블럼 장면

[현재 지원 게임·연동 제공 상태]   [현재 이용 안내]
[시작하기]                     [기본 하단 정보]
```

- 첫 화면에서 서비스 설명·주요 버튼·대표 장면이 함께 보이게 한다. 현재처럼 큰 여백을 지나야 예시가 나타나지 않게 한다.
- 헤더에는 로그인만 보조 행동으로 두고, 첫 본문과 맨 아래에서 가입 CTA를 제공한다. 본문에서 로그인과 가입을 동등한 두 큰 버튼으로 반복하지 않는다.
- 실제 최신 클랜 홈의 대표 장면을 기본으로 사용한다. 예시 클랜명·게임 ID·통계는 촬영용 예시 데이터로 교체하고 `예시 화면`을 표시한다. 실제 개인 이메일·QA 식별정보를 공개 홍보 이미지로 쓰지 않는다.
- 기능은 3개 사용 장면으로 압축한다. 스크림·대진표 등 나머지 기능은 짧은 보조 설명으로만 두고 핵심 장면을 밀어내지 않는다.
- 프로필은 게임별 전체 ID·소개·대표 엠블럼을 보여준다. 미구현 진열장이나 유료 구매를 가입 목적처럼 앞세우지 않는다.
- 지원 게임은 이름·로고와 제공 상태를 표시한다. 게임 활성 여부와 운영 연동 가능 여부를 함께 확인해 랜딩·게임 선택의 문구가 어긋나지 않게 한다. QA에서 활성인 것만으로 운영 지원을 약속하지 않는다.
- Free/Premium 명칭은 유지하되, 현재는 짧은 이용 안내로 낮춘다. 미출시 가격·혜택을 확정하거나 구매 버튼을 추가하지 않는다.
- 모바일은 소개 → CTA → 대표 장면 → 3개 사용 장면 순서다. 장면을 가로 캐러셀 안에 숨기지 않는다.

## 6. 로그인

```text
[로고 / 홈으로]                                             [테마]

          로그인                         [클랜 홈 정적 장면]
          계정으로 활동을 이어가세요.      일정과 기록을 이어가세요.
          이메일
          비밀번호                    ← 넓은 판촉 영역 대신 작은 맥락
          자동 로그인 [토글]
          공용 PC 안내
          [로그인]
          계정이 없으신가요? 회원가입
```

- 제목은 `로그인`으로 짧게 한다. 오류·입력·제출 버튼을 시선의 중심에 둔다.
- 이메일, 비밀번호 보기/숨기기, 실제 세션과 연결된 자동 로그인 토글을 유지한다. 자동 로그인 기본 OFF와 약 30일 안내를 바꾸지 않는다.
- 오른쪽 장면은 읽기 위한 정보가 아니라 서비스 맥락이다. 폼과 경쟁하지 않는 크기로 두고 모바일에서는 숨긴다.
- 입력 오류는 필드 아래, 로그인 자격·요청 실패는 폼 공통 영역에 표시한다. 계정 존재 여부를 추측하게 하는 문구나 새로운 잠금 횟수를 노출하지 않는다.
- 제출 중 버튼의 높이·위치는 유지하고 중복 제출을 막는다. 실패해도 이메일과 자동 로그인 선택을 보존하고 필요한 곳으로 초점을 이동한다.
- 비밀번호 찾기·Discord 로그인은 현재 구현돼 있지 않다. 이번 시각 개편에 동작 없는 링크를 추가하지 않는다. 복구 흐름 전체 구현은 별도 기능 범위다.

## 7. 회원가입

로그인과 같은 헤더·폼 폭·보조 패널을 사용한다. 세로가 긴 폼을 화면 중앙에 억지로 고정하지 않고, 작은 높이에서도 상단부터 자연스럽게 스크롤한다.

| 순서 | 구성 | 설계 이유 |
| --- | --- | --- |
| 1 | `회원가입` + `계정을 만든 뒤 게임을 연결해 클랜에 참여하세요.` | 무엇을 만드는지와 다음 단계를 한 문장으로 설명 |
| 2 | 이메일 | 로그인 수단부터 입력 |
| 3 | 비밀번호 + 보기/숨기기 + 규칙 안내 | 계정 정보를 한 덩어리로 완료 |
| 4 | 부가 정보: 출생연도(필수), 성별(선택·기본 비공개) | 현재 수집·검증은 유지하고 중요도만 낮춤 |
| 5 | 필수 동의 + 약관/개인정보 문서 보기 | 선택 정보와 필수 동의를 구분 |
| 6 | `계정 만들기` → 기존 계정 로그인 링크 | 주행동 하나로 종료 |

- 공통 닉네임을 다시 요구하지 않는다. `게임을 연결하면 게임별 ID로 활동해요.`처럼 전체 게임 ID 정책에 맞는 설명을 사용한다. `배틀태그 이름`만을 전제로 한 문구는 제거한다.
- 비밀번호의 영문·숫자·특수문자 8~72자 검증을 유지한다. 규칙을 placeholder와 긴 설명에 반복하지 않고 필드 아래 한 번 표시한다.
- 성별은 독립적인 큰 세그먼트보다 작은 선택 항목으로 둔다. 수집을 가입 후로 이동하거나 필수 출생연도를 삭제하는 정책 변경은 이번 안에 포함하지 않는다.
- 필수 동의는 현재 한 체크의 범위를 임의로 쪼개거나 넓히지 않는다. 약관·개인정보 문서의 실제 연결 경로를 구현 전에 확인한다. 링크가 준비되지 않았다면 `#` 링크로 완성 처리하지 않는다.
- 기존 출생연도 검증·미성년 안내는 보존한다. 연령 기준·보호자 동의 방식의 확정은 이 화면 배치 기획으로 대신하지 않는다.
- 이메일 확인이 필요하면 **동일한 폼 영역**에서 `이메일을 확인해 주세요`와 다음 행동을 보여준다. 가입 직후 인증 세션이 발급되면 안전한 원래 목적지로 이동한다.
- 메일 재전송·이메일 변경·비밀번호 확인 칸·강도 계기판을 이번 안에서 일괄 추가하지 않는다. 필요한 기능이 확인되면 별도 범위로 다룬다.

## 8. 게임 선택

### 구도

```text
[공통 헤더 / 게임 선택]                            [프로필] [테마]
게임 선택
플레이할 게임에서 클랜 활동을 이어가세요.

이용 중인 게임
[게임 로고·이름 | 전체 게임 ID | 내 클랜       | 클랜으로 이동 →]
[게임 로고·이름 | 전체 게임 ID | 신청 대기     | 신청 확인 →]

다른 게임
[게임 로고·이름 | 계정 연결 상태              | 게임 계정 연결 →]

지원 예정  ·  리그 오브 레전드  ·  PUBG …
```

- `이용 중인 게임`에는 현재 연결·소속·진행 중 신청이 있는 게임을 표시한다. 과거 이력·최근 이용 시각을 새로 조회하거나 수집하지 않는다. 같은 게임을 두 영역에 중복 표시하지 않는다.
- 헤더의 계정 메뉴에서 프로필·로그아웃 진입을 유지한다. 프로필 링크 하나로 바꾸면서 기존 로그아웃 동선을 없애지 않는다.
- 처음 가입한 사용자는 빈 `이용 중인 게임` 제목을 생략하고 이용 가능한 게임을 바로 보여준다.
- PC는 활성 게임 수에 따라 최대 2열의 정보 카드, 모바일은 1열 가로형 카드를 사용한다. 큰 이모지 대신 기존 게임 로고를 사용하고 정보 없는 썸네일 영역을 줄인다.
- 전체 게임 ID는 로그인한 본인의 연결된 계정만 표시한다. 현재 조회는 인증 여부만 가져오므로 ID를 보여주려면 본인 범위 조회 확장이 필요하다. 이메일을 게임 ID 대체값으로 쓰지 않는다.
- 카드 전체는 하나의 이동 링크다. 하단/우측의 행동 문구는 같은 링크 안에서 표시하고, 링크 안에 별도 버튼을 중첩하지 않는다.
- 활성 게임 6개 이하에서는 검색을 숨기는 안을 기본으로 한다. 7개 이상이면 제목 아래 작은 검색을 제공한다. 출시 예정 게임은 하단 작은 비활성 목록으로 내린다. 수량 기준은 UI 초안이다.

| 상태 | 표시와 주요 행동 | 기존 목적지 |
| --- | --- | --- |
| 인증됨 + 소속 있음 | 클랜명 · `클랜으로 이동` | 해당 클랜 홈 |
| 인증됨 + 신청 중 | 클랜명 · 승인 대기 · `신청 확인` | 현재 신청이 있는 가입 목록 |
| 인증됨 + 미소속 | 연결된 ID · `클랜 찾기` | 가입 목록 |
| 미인증 + 미소속 | `게임 계정 연결` | 게임 연동 화면 |
| 미인증 + 신청 중 | 신청 보류 이유 · `계정 연결 계속` | 게임 연동 화면 |
| 미인증 + 소속 있음 | 기존 소속 정보 · `게임 계정 다시 연결` | 기존 `reauth=1` 경로 |
| 지원 예정 | `지원 예정`, 이동 불가 | 없음 |
| 조회 실패 | 목록 영역 안에 오류와 재시도 | 미소속으로 오인해 표시하지 않음 |

운영에서 신규 연동을 제공하지 못하면 미인증 카드의 행동은 `연결 상태 보기`로 바꾸고 연동 화면에서 `계정 연결 준비 중`을 명확히 알린다. QA 시뮬레이터로 성공한 화면을 실제 외부 OAuth 제공의 증거로 삼지 않는다.

## 9. 게임 인증·재연동

게임 인증을 로그인·회원가입과 별개인 **독립 상세 설계 대상**으로 다룬다. 전체 구도·입력 계약·상태·이동·검증은 [게임 인증 상세](../02-design/entry-experience/05-game-auth.md)에 둔다.

```text
[공통 헤더 / 게임 계정 연결]                    [계정 메뉴] [테마]
[게임 선택 ✓ — 게임 계정 연결 — 클랜 참여]
[게임 로고·게임명]
게임 계정 연결 / 게임 계정 다시 연결
게임별 ID로 클랜에 참여하기 위한 단계임을 설명
[기존 연결 ID·재확인 이유: 재연동일 때]
[제공자·실제 제공 상태]
[환경에 맞는 연결 동작 또는 준비 중 안내]
[필드/공통 오류]
[게임 선택으로 / 프로필로 돌아가기]
```

- PC 최대 560px 안팎의 연결 영역, 모바일 1열로 구성하고 정보 없는 큰 좌우 판촉 패널은 두지 않는다.
- QA에서는 `테스트 연결`을 명시하고 배틀태그·라이엇 ID 전체를 입력한다. 운영 신규 연동 미제공이면 입력란·실제 제공자 로그인 버튼을 노출하지 않고 준비 상태와 복귀 행동을 제공한다.
- 실제 OAuth를 제공할 때의 외부 승인·취소·실패·계정 불일치는 별도 출시 의존성으로 설계한다. 화면 기획만으로 외부 연동이 구현됐다고 표시하지 않는다.
- 최초 연결·재연동·이미 연결됨을 구분한다. 재연동은 `reauth=1` 등 진입 계약을 확인하고, ID/기존 소속·기록이 조용히 바뀌는 표현을 만들지 않는다.
- 인증 성공 목적지와 취소 목적지를 분리한다. 취소를 미인증 보호 URL로 돌려 인증 화면이 반복되지 않게 한다. 게임 선택에서 왔으면 게임 선택, 프로필에서 재연동했으면 프로필로 돌아간다.

## 10. 클랜 가입

### 목록과 상세를 한 흐름으로 연결

```text
[공통 헤더]                                    [게임 선택] [프로필]
오버워치 / 클랜 찾기                                  클랜 만들기
[게임 선택 ✓ — 게임 계정 연결 ✓ — 클랜 참여]
[현재 신청: 클랜명 · 승인 대기 · 상세 보기 · 신청 취소]  ← 있을 때 1회
[클랜명 검색                     검색] [지향] [모집 티어] [초기화]

[목록 약 44%]                         [선택 클랜 상세 약 56%]
 아이콘·이름·지향·모집 티어             배너·아이콘·클랜명
 소개 1~2줄·인원/정원                  소개 → 모집 조건 → 규칙
 목록 선택 강조                        외부 커뮤니티 링크(있을 때)
 …                                    신청에 사용할 내 전체 게임 ID
 이전 / 다음                          메시지(선택)
                                      [이 클랜에 가입 신청]
```

- 검색과 필터는 한 흐름으로 묶는다. 검색·필터 제출 버튼을 따로 중복하지 않고 `검색` 한 번으로 적용한다. 결과 수·초기화·페이지 이동을 가까이 둔다.
- 가입을 기본 화면으로 삼고 `클랜 만들기`는 제목 옆 보조 진입으로 낮춘다. 누르면 기존 생성 폼을 보여주고 `클랜 찾기로 돌아가기`를 제공한다. 생성 후 리더 환영·Discord 안내와 건너뛰기는 보존한다.
- 목록에는 이름·아이콘, 지향, 모집 티어, 소개 1~2줄, 인원/정원, 마감 여부를 표시한다. Premium은 모집 판단의 주정보가 아니므로 목록에서 제외한다. 없는 활동시간·접속률·추천 점수·배지 수를 만들어 넣지 않는다.
- 태그는 목록에서 최대 2~3개만 보여주고 전체는 상세로 보낸다. 정원 마감 클랜도 열람은 가능하지만 신청은 할 수 없게 한다.
- 클랜 홈의 기존 배너·아이콘을 상세에 재사용한다. 현재 목록 조회에는 해당 필드가 없으므로 필요한 필드만 추가한다. 이미지가 없으면 공통 기본 클랜 아이콘과 단색 배경을 사용한다.
- PC 최초 진입은 첫 결과의 소개를 미리 보여주되 자동 신청하지 않는다. 선택 강조와 상세 제목을 일치시킨다. 결과가 바뀌면 남아 있는 선택을 유지하고, 제외된 선택은 새 결과의 첫 항목으로 바꾼다.
- 상세에서 소개·모집 조건·규칙을 읽고 바로 신청한다. 선택 메시지와 `신청에 사용할 게임 ID`를 한 영역으로 묶는다. 게임 ID는 읽기 전용이며 변경은 기존 연결 관리로 안내한다.
- 기존 신청중 안내와 고정 신청 카드 두 개를 **현재 신청 요약 하나**로 합친다. 검색 결과가 없어도 남고, 클릭하면 같은 상세 영역을 연다. 같은 클랜을 목록에 다시 중복 노출하지 않는다.
- 신청 직후 같은 상세에서 `신청 완료 · 운영진 승인 대기`로 바꾼다. 성공 토스트만 띄우고 끝내거나 승인된 것처럼 클랜 내부로 보내지 않는다.
- 다른 클랜에 신청할 때는 기존 신청을 바꾼다는 확인을 유지한다. 취소·교체 후 실패·재가입 제한 등 서버 결과를 상세 안에서 설명한다.

### 모바일

- 첫 화면은 검색·현재 신청·클랜 목록이다. 카드를 누르면 전체 화면 상세를 연다. 긴 규칙·키보드·신청 폼을 수용하도록 작은 고정 높이 바텀시트는 사용하지 않는다.
- 상단에 `클랜 목록으로`와 클랜명을 두고, 상세를 닫으면 검색어·필터·페이지·목록 스크롤과 선택 위치를 복원한다. 브라우저 뒤로가기도 상세부터 닫는다.
- 신청 영역은 상세 하단에 둔다. 주요 버튼을 하단에 고정하는 경우 입력창·안전 영역·본문 끝을 가리지 않게 하며, 메시지 입력 중에도 오류를 읽을 수 있게 한다.
- 다른 클랜으로 전환할 때 작성 중 메시지를 조용히 잃지 않도록 확인한다. 취소하면 기존 상세와 입력을 유지한다.

## 11. 공통 상태 처리

회원가입·로그인은 ClanSync 계정 진입, 게임 선택 이후의 단계 표시는 `게임 선택 → 게임 계정 연결 → 클랜 참여`로 구분한다. [공통 상세 규칙](../02-design/entry-experience/README.md)의 이동·복귀·오류·초안 계약을 각 화면에 함께 적용한다.

| 상황 | 화면 처리 기준 |
| --- | --- |
| 검색·필터·페이지 갱신 | 헤더·제목·검색·필터·현재 신청은 유지. 목록/상세의 데이터 영역만 갱신하고 요청 조건이 다른 오래된 상세를 새 결과처럼 표시하지 않음 |
| 로딩 | 기존 목록/상세 외곽 크기 안에서 스켈레톤·갱신 상태 표시. 기간/필터 값을 카드 `key`로 써서 화면 전체를 재생성하지 않음 |
| 빈 결과 | 해당 영역 안에 이유와 검색 초기화 제공. 페이지 전체를 빈 안내로 대체하지 않음 |
| 목록 오류 | 기존 필터 유지 + 해당 영역 재시도. 실패를 `클랜 0개`로 표시하지 않음 |
| 신청 중 | 신청 버튼 중복 실행 차단, 입력과 주변 맥락 유지 |
| 정원·모집 상태 변경 | 제출 시 서버 판정 반영, 신청되지 않았음을 명확히 표시 |
| 다른 클랜 신청으로 교체 | 기존 대상·새 대상을 확인. 새 신청 실패 시 실제 남아 있는 신청 상태를 다시 조회해 표시 |
| 신청 승인/취소 후 재방문 | 서버 소속·신청 결과를 다시 읽음. 다음 진입 때 소속이면 클랜으로 이동; 새 실시간 구독은 별도 검토 |
| 계정·게임·권한 변경 | 이전 응답을 폐기. 다른 계정의 ID·신청·클랜 내용을 남기지 않음 |
| 키보드·보조기기 | 읽기 순서와 시각 순서 일치, 선택/오류 상태 이름 제공, 모바일 상세 초점 이동·복귀, 모션 감소 대응 |

## 12. 구현 범위와 순서 제안

| 순서 | 작업 묶음 | 주 변경 지점 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 공통 표면·헤더·인증 배치 | `entry` 셸/CSS, 로그인·가입 폼, `AccountShell` | 폼 정책·목적지 유지, PC/모바일 구도·오류 상태 정리 |
| 2 | 게임 선택·게임 인증 | 게임 조회·카드·기존 상태 라우터·연동 화면 | 게임/상태별 다음 행동 명확, 6가지 인증·소속 조합, 재연동·취소 복귀 유지 |
| 3 | 클랜 탐색·신청 | 클랜 목록 페이지·`ClanJoinList`·생성 진입 | 목록→상세→신청 연결, 대기 중복 제거, 모바일 복귀 보존 |
| 4 | 랜딩·대표 이미지 | 랜딩·기능 소개·미리보기 자산 | 최신 구현 화면으로 설명, 지원/연동 상태와 문구 일치 |

랜딩 이미지는 내부 화면 배치를 먼저 확정한 뒤 교체한다. 이번 구현 제안에 프로필 자체 개편·새 진열장·추천 알고리즘·가입 정책 개정·운영 DB 변경·배포를 묶지 않는다.

### 구현 전에 확인할 실제 의존성

1. **지원 상태의 기준:** 게임 활성 상태와 운영 연동 제공 상태를 어떻게 함께 표현할지 정한다. QA의 활성 게임 목록과 현재 랜딩의 고정 문구를 그대로 섞지 않는다.
2. **표시 데이터:** 본인의 전체 게임 ID와 클랜 배너/아이콘에 필요한 조회 필드·권한을 확인한다. 목록 전체에 구성원·개인 통계를 추가 조회하지 않는다.
3. **필수 문서 연결:** 실제 약관·개인정보 문서의 경로와 내용 확인이 필요하다. 현재 수집 기준과 미성년 안내를 디자인 작업으로 임의 변경하지 않는다.
4. **신청 교체 실패:** 현재 액션은 기존 신청 취소 후 새 신청을 시도한다. 화면 이동만 바꿔도 실패 상태를 정확히 알려야 하며, ‘항상 기존 신청 보존’을 약속하려면 원자적 교체 등 별도 데이터 동작 설계·검증이 필요하다.
5. **재연동·취소:** 프로필에서 계정 변경 시 재연동 진입을 건너뛰지 않는지 확인한다. `next`는 성공 후 목적지에 쓰고 취소는 안전한 게임 선택/프로필 복귀로 분리한다.

## 13. 검증 기준

**이번 변경은 문서만이다.** 링크·기술 근거·제안/현재 상태 구분을 확인한다. 앱 빌드·가입 E2E·DB 쓰기 검증은 실행하지 않는다.

구현 시에는 다음 범위를 실제 변경 위험에 맞춰 적용한다.

- 공통: 320/390/768/1280px, 다크/라이트, 긴 게임 ID·클랜명, 키보드 초점·상세 복귀, 확대/모션 감소, 로딩·빈 결과·실패 시 영역 유지.
- 인증: 필수값·오류·중복 제출·확인 메일 안내 분기·자동 로그인 선택·안전한 `next`·로그인/가입 왕복을 확인한다. 실제 메일 수신은 QA 메일 환경의 제공 여부와 별도로 기록한다.
- 게임 선택: 인증 × 소속 6가지 조합, 지원 예정, 조회 실패, 다중 게임, 미가입 프로필 접근을 확인한다.
- 게임 인증: 최초 연결·재연동·이미 연결·운영 미제공·QA 입력 오류·취소/거부·실패·계정 불일치와 안전한 성공/취소 복귀를 구분한다. 실제 OAuth 관련 검증은 해당 기능이 구현된 뒤에만 완료로 기록한다.
- 클랜 가입: 검색/필터/페이지·모바일 복귀, 메시지 초안, 새 신청·승인 대기·취소·교체 실패·정원 마감·재가입 제한·권한 변경을 별도 임시 사용자/클랜으로 확인한다.
- 시작점: [온보딩](../../e2e/onboarding.spec.ts), [인증](../../e2e/auth-performance.spec.ts), [세션](../../e2e/session-cookies.spec.ts), [재가입](../../e2e/clan-membership-return.spec.ts), [프로필 탐색](../../e2e/profile-navigation.spec.ts). 테스트가 현재 제안 전체를 이미 검증한다는 뜻은 아니다.
- [기존 가입 흐름 테스트](../../e2e/join-request-flow.spec.ts)는 공유 QA 계정 변경을 포함하므로 그대로 실행하지 않는다. 필요한 시나리오를 격리된 임시 데이터로 옮긴다. `E2E_SKIP_SEED=1`과 별도 E2E 서버를 사용한다.
- 인증·권한·공통 라우팅·조회 범위를 실제로 바꾸면 관련 회귀와 빌드를 포함한다. QA 시드 재실행, 운영 DB 적용, 수동 배포는 이번 작업 범위 밖이다.
