## 최초 리뷰 평가

**기능 범위가 갖춰진 MVP이며, 외부 사용자 운영 전에 DB 권한과 상태 변경의 정합성을 보강해야 한다.** 화면·라우트의 구현 완료를 보안·운영 검증 완료와 구분해야 한다. M8 종료 감사는 완료 처리하지 않는다.

| 영역 | 평가와 근거 |
|------|------------|
| 제품 범위 | 클랜 온보딩, 내전, 일정, 통계, 상점, 커뮤니티까지 실제 라우트와 서버 액션으로 연결되어 있다. |
| 코드 구조 | UI·서버 액션·도메인 헬퍼·DB 마이그레이션의 구분, 생성 DB 타입, 공통 권한 헬퍼는 유지할 만하다. |
| 데이터 접근 통제 | 앱의 검증보다 DB의 쓰기·실행 권한이 넓다. 일반 사용자가 앱을 거치지 않고 API를 호출하는 경우를 우선 보완해야 한다. |
| 상태 변경 | 일정 재예약과 승인 처리의 여러 DB 요청이 일관된 하나의 작업으로 묶이지 않은 곳이 있다. |
| 검증 | 빌드·공개 화면 스모크는 통과했으나 앱 린트가 실패한다. UI 스모크 중심 테스트가 DB 권한·경합 문제를 보장하지 않는다. |
| 문서 | 슬라이스·정책 결정은 유용하다. 현황표와 초기 로드맵의 중복으로 상태가 어긋나 있었으며 이번에 정리했다. |

## 최초 리뷰 결함과 재현 근거

### R01 · P1 — 서비스 전용 RPC의 실행 권한이 남아 있음

- **위치:** [0006 기본 권한](../../supabase/migrations/0006_postgrest_api_grants.sql#L30), [구매 RPC](../../supabase/migrations/0015_store_profile_entrance_nameplate.sql#L25), [클랜 환불](../../supabase/migrations/0036_void_clan_store_purchase_rpc.sql), [개인 환불](../../supabase/migrations/0038_void_personal_store_purchase_rpc.sql).
- **원인:** `anon, authenticated`에 함수 EXECUTE를 직접 기본 부여한다. 이후 서비스 전용 함수에서 `REVOKE ... FROM PUBLIC`만 해도 두 역할에 직접 부여된 권한은 남는다. `SECURITY DEFINER` 구매·환불 함수가 호출자의 실제 인증 대신 입력 `p_actor_id`를 신뢰한다.
- **영향/재현 조건:** 해당 권한으로 생성된 함수가 있는 DB에서 공개 API를 통해 다른 클랜원의 ID를 전달하면 그 사람의 권한·잔액으로 구매·환불을 시도할 수 있다. 서버 액션의 검사는 이 직접 호출을 막지 않는다.
- **수정:** 서비스 전용 함수의 `PUBLIC, anon, authenticated` 실행 권한을 모두 회수하고 기본 권한도 정리한다. 인증 사용자용 RPC는 개별 허용한다. 기존 마이그레이션을 고치는 것만으로 배포된 DB가 교정되지 않으므로 새 마이그레이션이 필요하다.
- **완료 검증:** 익명·일반 사용자 직접 호출 거부, 서비스 호출 성공, 기존 사용자용 RPC의 정상 동작을 각각 확인한다. [공식 함수 권한 안내](https://supabase.com/docs/guides/database/functions#function-privileges).

### R02 · P1 — 개인 코인 잔액을 본인이 직접 변경 가능

- **위치:** [users 자기 행 수정 정책](../../supabase/migrations/0001_init.sql#L65), [전체 UPDATE 권한](../../supabase/migrations/0006_postgrest_api_grants.sql#L12), [자기 행 INSERT](../../supabase/migrations/0007_service_role_schema_usage_users_self_insert.sql).
- **원인:** 자기 행인지 확인하지만 수정할 컬럼은 제한하지 않는다. 잔액 보호 트리거나 컬럼별 권한 제한도 없다.
- **영향/재현 조건:** 로그인 사용자가 자신의 `users.coin_balance`를 임의의 양수로 바꾸면 원장 없이 잔액을 만들 수 있고, 상점은 그 잔액을 사용한다.
- **수정:** 전체 INSERT/UPDATE 권한을 회수하고 사용자 수정 가능 컬럼만 허용한다. 생성 경로에서도 임의 초기 잔액을 막는다. 잔액·원장은 서버의 원자적 처리로만 변경한다.
- **완료 검증:** 직접 잔액 변경 거부, 정상 프로필 수정·회원가입·구매·환불 성공, 원장과 잔액 일치. 행 제한과 컬럼 제한은 별개다. [공식 RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security).

### R03 · P1 — 게임 인증 상태를 사용자 API로 위조 가능

- **위치:** [게임 프로필 INSERT/UPDATE 정책](../../supabase/migrations/0001_init.sql#L121), [온보딩 판정](../../src/lib/onboarding/load-game-onboarding.ts).
- **원인:** 자기 게임 프로필에 `is_verified=true`와 임의의 `game_uid`를 쓸 수 있다. 온보딩은 이 값을 신뢰한다.
- **영향/재현 조건:** 개발용 연동 시뮬레이터가 비활성화되어도 로그인 사용자가 직접 API로 인증 표시를 만들고 게임·클랜 온보딩 조건을 통과한다.
- **수정:** 게임 인증 증빙은 서버만 기록하도록 제한한다. 개발 시뮬레이터도 환경·사용자를 서버에서 검사한 뒤 서비스 클라이언트로 기록한다.
- **완료 검증:** 사용자 직접 INSERT/UPDATE로 인증 위조 불가, 정상 서버 인증 및 개발 환경 시뮬레이터 성공, 비개발 환경 시뮬레이터 차단.

### R04 · P1 — 재귀 RLS와 오류 무시로 클랜 권한 설정이 기본값으로 대체됨

- **위치:** [자기 테이블을 다시 조회하는 정책](../../supabase/migrations/0001_init.sql#L220), [clan_settings 정책](../../supabase/migrations/0004_main_clan_shell.sql#L29), [권한 조회](../../src/lib/clan/has-clan-permission.ts#L33).
- **원인:** `clan_members_same_clan_select`가 동일 테이블을 조회해 재귀 오류 대상이다. `0017`·`0018`은 밸런스 정책을 교체했지만 이 원래 정책은 남아 있다. 설정 조회가 실패해도 `hasClanPermission`은 오류를 확인하지 않고 기본 허용 목록을 적용한다.
- **영향/재현 조건:** 저장소 정책을 적용한 DB에서 일반 사용자로 설정을 조회하면 실패할 수 있다. `kick_member: ["leader"]`로 제한한 클랜에서도 운영진에게 기본 강퇴 권한이 적용되는 경로가 생긴다.
- **수정:** 원래 재귀 정책을 인증된 사용자 기준의 재귀 없는 헬퍼로 교체한다. 설정 행·권한 조회 실패와 정상적인 기본 설정을 구분하고 실패 시 작업을 거부한다.
- **완료 검증:** 네 역할의 SELECT 허용/거부, 클랜별 권한 재정의 반영, DB 오류 시 권한 확대 없이 거부.

### R05 · P1 — LFG 신청자가 자신을 수락 처리 가능

- **위치:** [LFG 신청자 정책](../../supabase/migrations/0011_main_game_community_m7.sql#L166).
- **원인:** UPDATE 정책이 `applicant_user_id`만 확인하고 `status`·`post_id` 변경을 제한하지 않는다. INSERT도 초기 상태를 제한하지 않는다.
- **영향/재현 조건:** 신청자가 자신의 신청을 `accepted`로 바꾸고 `resolved_at`을 채우면 모집자 승인을 우회할 수 있다. 서버 액션의 모집자 검사와 정원 처리도 거치지 않는다.
- **수정:** 생성 상태를 `applied`로 제한하고, 신청자는 자신의 미처리 신청 취소만 수행하도록 한다. 수락·거절은 권한·대상·상태 전이를 검증하는 RPC로 처리한다.
- **완료 검증:** 신청자 수락·다른 모집으로 이동 거부, 정상 신청·취소·모집자 승인 성공, 마감 후 승인 거부.

### R06 · P1 — 일정 수정·스크림 재확정에서 알림 고유키 충돌

- **위치:** [알림 INSERT](../../src/lib/clan/schedule-clan-event-inapp-notifications.ts#L89), [고유 인덱스](../../supabase/migrations/0031_notification_log_poll_mvp.sql#L54), [스크림 알림 재예약](../../supabase/migrations/0041_scrim_rooms_clan_events_sync.sql#L382).
- **원인:** 기존 예약을 `cancelled`로 바꾸고 같은 이벤트·회차·슬롯·수신자로 새 행을 INSERT한다. 고유 인덱스는 취소 상태와 시각을 구분하지 않아 기존 행과 충돌한다.
- **영향/재현 조건:** 알림이 예약된 미래 단발 일정의 제목·시각을 수정하면 일정은 저장되지만 알림은 취소된 채 재예약에 실패한다. 같은 구조의 스크림 트리거에서는 확정된 미래 경기 수정·재확정이 트랜잭션 오류로 실패한다.
- **수정:** 기존 예약을 원자적으로 갱신하거나 예약 버전을 도입해 이력·재예약·발송 중복 방지 기준을 함께 정의한다. 단순 오류 무시로 처리하지 않는다.
- **완료 검증:** 제목만 수정, 일시 변경, 취소 후 재확정, 반복 일정 수정에서 정상 예약이 남고 중복 발송은 없어야 한다.

### R07 · P2 — 일정 수정 시 서버 시간대로 재해석

- **위치:** [서버의 로컬 시각 재파싱](../../src/app/actions/clan-events.ts#L318), [브라우저 ISO 변환](../../src/components/main-clan/clan-events-view.tsx#L273).
- **원인:** 브라우저가 이미 보낸 시간대가 포함된 ISO 값보다 시간대 없는 `start_at_local`을 우선해 서버에서 다시 `Date`로 파싱한다.
- **영향/재현 조건:** 브라우저는 한국, 서버는 UTC일 때 20:00 입력을 제목만 수정해도 `11:00Z`에서 `20:00Z`로 덮어써 실제 일정이 9시간 늦어진다. UTC Node 프로세스에서 두 파싱 결과의 9시간 차이를 확인했다.
- **수정:** 브라우저가 변환한 ISO 시각을 검증해 사용한다. 시간대 없는 문자열은 거부하거나 명시한 시간대와 함께 처리한다.
- **완료 검증:** 브라우저·서버 시간대를 다르게 두고 생성→제목만 수정→시각 수정 시 의도한 시각이 유지되는지 확인한다.

### R08 · P2 — 동시 가입 승인 시 클랜 정원 초과

- **위치:** [가입 승인 정원 조회·등록](../../src/app/actions/game-clan-onboarding.ts#L541).
- **원인:** 정원 조회, 멤버 등록, 신청 처리 완료가 별도 DB 요청이며 클랜·신청 행을 잠그지 않는다.
- **영향/재현 조건:** 30명 정원에 29명인 클랜에서 운영진 둘이 다른 신청을 동시에 승인하면 둘 다 정원 여유를 읽어 31명이 될 수 있다. 취소·거절과 승인 간 경합도 같은 묶음에서 다뤄야 한다.
- **수정:** 클랜·신청 행 잠금과 상태·정원 검증부터 멤버 등록·신청 전환까지 단일 트랜잭션 RPC로 처리한다.
- **완료 검증:** 두 동시 승인 중 한 건만 성공, 승인·취소 경합의 결과 일관성, 재요청의 중복 처리 방지.

### R09 · P2 — LFG 동시 수락 시 모집 정원 초과

- **위치:** [수락 후 COUNT·마감](../../src/app/actions/main-game-community.ts#L194).
- **원인:** 수락 행 변경 후 수락 수를 세고 모집을 마감하는 요청이 분리되어 있다. 승인 전에 잠금으로 정원을 확보하지 않는다.
- **영향/재현 조건:** 1명 모집의 신청 두 건을 서로 다른 탭에서 동시에 수락하면 모두 `open`을 읽고 두 명이 수락될 수 있다.
- **수정:** 모집 행을 잠그고 상태·마감·남은 인원을 검사한 후 수락과 모집 마감을 한 트랜잭션으로 수행한다.
- **완료 검증:** 동시 수락이 정원을 넘지 않고, 이미 마감된 모집의 수락은 거부되며, 남은 신청의 상태도 일관되어야 한다.

## 최초 리뷰 검증 결과와 유지보수 과제

| 실행 | 결과 |
|------|------|
| `npm run build` | 통과: 컴파일·TypeScript·라우트 생성 |
| `npx eslint src middleware.ts playwright.config.ts e2e` | 오류 3건·경고 1건 |
| `npm run lint` | 오류 20건·경고 100건. 로컬 아이콘 원본과 정적 목업이 검사 범위에 포함됨 |
| `E2E_SKIP_SEED=1 npm run test:e2e -- e2e/smoke.spec.ts` | 1건 통과: 랜딩·로그인 표시. Windows에서는 환경변수를 PowerShell 방식으로 설정 |
| UTC 시간 파싱 비교 | 브라우저 ISO `11:00Z`가 서버 로컬 문자열 파싱으로 `20:00Z`가 되는 차이 확인 |

앱 린트 오류는 [영웅 밴](../../src/components/main-clan/clan-balance-hero-ban-client.tsx#L72), [일정 참석자](../../src/components/main-clan/clan-events-view.tsx#L159), [토스트](../../src/components/ui/sonner.tsx#L16)의 `set-state-in-effect` 3건이다. [통계](../../src/components/main-clan/clan-stats-view.tsx#L280)에 미사용 변수 경고가 있다. 경고를 숨기기보다 상태 동기화 필요성을 확인해 수정한다. 전체 린트에서는 로컬 vendor 파일을 제외하고 정적 목업의 검사 정책을 분리할 필요가 있다.

`supabase/tests/`는 없고 현재 E2E는 화면·정상 사용자 흐름 중심이다. `.github/workflows/`의 두 파일은 수동 배포용으로, PR마다 lint·권한 검증을 강제하는 CI는 저장소에 없다. 외부 배포 서비스의 별도 검사 설정은 확인하지 않았다.

`middleware.ts`에서 인증·온보딩 DB 조회를 수행하므로 후속 성능 점검 시 중복 조회와 Proxy 전환도 검토할 수 있다. 현재 빌드는 통과하며 이번 결함 9건보다 우선순위가 낮다. 설치된 Next.js의 [Proxy 문서](../../node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md)를 기준으로 판단한다.
