# 기획·디자인 고도화 논의

## 이 문서의 역할

2026-09-15 기획·디자인 리뷰에서 나온 제안을 구체화하는 작업 문서다. 사용자는 2026-09-16 문서화 요청에서 당분간 이 내용을 이어서 논의하는 방식을 선택했다.

- **확정된 작업 방향:** 제안을 문서화하고, 주제별로 사용자 흐름·화면·정책을 구체화한다.
- **제안의 상태:** 아래 7개 주제는 논의 중이다. `D-UX-01`의 기본은 사용자가 확정한 **클랜원 목록 직접 선택**과 기존 설계인 **최근 참여순 정렬**이다. **대기방 화면 연결은 프로젝트 적용 방향을 확정**했고 게임사 문의는 후속으로 진행한다. 수동 선택 화면안·자동화 상세·나머지 정책은 미결이다.
- **관찰 기준:** 2026-09-15 운영 대시보드·밸런스 화면, 정적 목업, 해당 상세 기획. 사용자 인터뷰나 사용성 실험 결과는 아니며, 기대 효과는 검증할 가설이다.
- **문서 관계:** 결정 상태·확정 내용은 [decisions.md](./decisions.md)의 `D-UX-01~07`로 추적한다. 이 문서는 문제·대안·질문을 구체화한다. 현재 구현 상태는 [Phase 2 현황](../TODO_Phase2.md)을 참조한다.
- 새 결정이 확정되기 전까지 기존 정책이 유효하다. 확정할 때 해당 기존 결정과 PRD·페이지·슬라이스·권한/플랜 표를 함께 갱신한다. 구현·검증 완료는 별도로 기록한다.

## 중심 가설과 유지할 장점

**“클랜원들이 모여 내전 한 번을 준비하고, 함께 플레이하고, 기록을 남긴다”는 경험을 연결하면 운영 부담과 구성원의 참여 부담을 줄일 수 있다.**

목업의 어두운 색감, 클랜 정체성을 드러내는 배너, 블루·레드 팀의 명확한 구분은 유지할 가치가 있다. 고도화에서는 역할과 상황에 따라 다음 행동이 눈에 들어오도록 정보 순서를 다듬는다.

첫 대상으로는 기존에 내전을 운영하는 클랜과 운영진을 제안한다. 신규 클랜 탐색·공개 커뮤니티까지 동시에 우선할지는 아직 결정하지 않았다.

## D-UX-01. 내전 전체 흐름

**현재 관찰**

내전 일정은 등록할 수 있지만 참석 응답(RSVP)은 스크림에만 허용한다. 이는 현재 [이벤트 명세](./pages/11-Clan-Events.md)의 정책이며, 내전 RSVP가 없다는 사실 자체를 결함으로 보지 않는다. 기존 밸런스 화면은 운영진이 출전 명단·포지션을 편성하는 구조다.

**사용자 피드백 — 2026-09-16**

- 웹·앱을 사용하는 것 자체가 게임을 하려는 구성원에게 귀찮은 일이 될 수 있다.
- 사용자는 사전 계획보다 ‘오늘 내전 참여해 볼까?’ 하고 그때 합류하는 사람이 많다고 본다. 참가 신청과 체크인은 부담을 더할 수 있다. 이는 사용자의 운영 관점이며 전체 사용자 집단을 측정한 결과는 아니다.
- **확인된 운영 맥락:** 운영진은 **게임 내 대기방에 들어온 사람**을 보고 지금 내전할 인원을 파악한다.
- **사용자가 확정한 기본 사양:** 클랜원 목록에서 참가자를 직접 선택한다. 이 경로를 유지하면서 입력 행위를 크게 줄일 보조 방식을 검토한다.
- **추가 문제 제기:** OCR도 스크린샷 촬영·웹 전환·붙여넣기·인식 결과 확인이 필요하다. 인식 기술 도입만으로 조작 부담이 사라지지는 않는다.
- **기존 설계 확인:** 사용자는 기본 정렬을 최근 참여순으로 두어 최근 함께한 사람을 목록 위에서 선택하도록 이미 설계했다. 목업의 플레이어 정렬에도 ‘최근 참여 순’이 첫 옵션으로 있다. 이를 새로운 고도화 아이디어로 다시 제안하지 않는다.
- **대기방 연결 채택:** 사용자가 게임사 문의는 나중에 하더라도 프로젝트에 적용하는 방향을 선택했다. 정책 적합성 미확인 사실을 유지하되 문의 회신을 구현 착수의 선행 승인 조건으로 두지 않는다.
- **실제 라운드 운영:** 대기방에는 해당 라운드 출전자 10명과 관전자(+α)가 있다. 사용자는 출전자 10명만 선택해 두고 라운드가 끝나면 변경된 사람을 빼고 넣는 방식을 사용해 왔다. 전체 대기방 인원을 매 판 새로 등록·분류할 필요가 있다는 가정을 두지 않는다.
- **공간 배치 기준:** 사용자가 제공한 대기방 화면은 왼쪽 1팀 5칸·오른쪽 2팀 5칸·아래 관전자 구조다. 사용자는 게임과 웹 사이에서 어디까지 수정했는지 놓치지 않도록 이 환경을 최대한 맞추길 요청했다. 출전자 10명을 별도 한 줄 목록으로 재구성했던 안을 수정한다.
- **입력 조작 단순화:** 사용자는 기존에 자리 우클릭으로 비우고, 이름을 고르면 1팀 1~5번 → 2팀 1~5번 순서로 자동 입력했다. 자리 선택·비우기 버튼·맞교환·현재 입력 위치 문구를 추가한 안을 줄이고, 하단 클랜원 목록의 선택/미선택을 명확히 구분하도록 요청했다.
- **역할·표시 확정:** 관전자는 등록하지 않으므로 입력 화면에서 영역을 제거한다. 양 팀은 위부터 **딜·딜·탱·힐·힐**로 고정하고 기존 편집 목업처럼 중앙에 역할 아이콘을 표시한다. 클랜원 체크 표시는 제거하며 `편성하기` 버튼 행 왼쪽에는 선택됨/미선택 색상 범례만 둔다.
- **숨김안·드래그 요청:** 이후 사용자는 색상 범례도 제거하고 선택한 사람을 하단 목록에서 숨기는 안을 제안했다. 위 명단에서 이름을 드래그해 위치를 이동·교환하는 동작은 추가하도록 요청했다. 범례 제거와 드래그를 반영하고, 숨김으로 후보 목록이 당겨지는 사용성은 화면안에서 검토한다.

**초기안에서 수정한 점**

초기안의 `일정 등록 → 참가 신청 → 체크인 → 편성`을 기본 흐름으로 제안했던 판단을 철회한다. 사전 신청을 전제로 한 행사 흐름이 즉흥적인 내전에 적합한지 검토가 부족했다. 일정은 내전 시작의 필수 선행 단계로 제안하지 않는다. 별도 예약·참가 기능이 필요한지는 수요를 확인한 뒤 검토한다. 스크림의 기존 RSVP 정책을 변경한다는 뜻은 아니다.

**수정 제안 — 게임 대기방 기준, 운영진 중심**

`게임 대기방에 모임 → 운영진이 모인 명단 반영 → 팀 편성 → 게임 진행 → 운영진 결과 입력 → 같은 명단으로 다음 판`

| 장면 | 구성원의 행동 | 웹에서 지원할 운영진의 행동 |
|------|----------------|----------------------------|
| 첫 판 준비 | 평소처럼 게임 대기방에 합류 | 등록된 클랜원 중 대기방 인원을 빠르게 선택해 편성 |
| 팀 확정 | 안내받은 팀으로 이동해 플레이 | 확정된 팀을 게임 채팅 등에 전달하기 쉽게 복사하는 기능 검토 |
| 경기 종료 | 다음 판 참여 여부를 기존 방식으로 전달 | 결과 입력 후 명단·설정을 유지해 다음 판 준비 |
| 중간 합류·이탈 | 게임 대기방에서 합류·이탈 의사 전달 | 바뀐 사람만 추가·제외하고 필요한 자리만 교체 |
| 기록 확인 | 원할 때 웹에서 자신의 기록 열람 | 실제 출전자 기준으로 기록 확인·정정 |

이 표는 밴픽을 사용하지 않는 기본 경로의 제안이다. 밴픽·예측에 참여하는 흐름은 아래 미결 사항으로 분리한다.

**제안의 설계 기준**

- 이미 등록된 구성원은 일반 내전 참가를 위해 매번 웹에 로그인하거나 참가·체크인·준비 완료 버튼을 누르지 않아도 되는 것을 목표로 한다. 최초 가입·게임 인증·클랜 등록 요건을 없앤다는 의미는 아니다.
- 게임 대기방에서 확인한 명단을 웹에 중복 입력하는 운영진의 부담도 줄인다. 다음 판마다 명단을 처음부터 다시 고르지 않는 흐름을 우선한다.
- **게임 대기방 입장과 웹 접속은 다르다.** 웹 접속 여부로 참가 의사·출전·불참·노쇼를 추정하지 않는다.
- 경기 기록은 실제로 배치해 출전한 사람을 기준으로 연결하는 안을 검토한다. 미가입자·인증되지 않은 사람의 기록 처리 방식은 별도로 결정한다.
- 명단 입력은 기존 클랜원 직접 선택을 기본으로 하고, 적용하기로 한 대기방 화면 연결을 보조 경로로 둔다. **OCR은 현재 미구현**이며 첫 연결·인식·오인식 정정까지 포함해 입력 시간이 줄어드는지 검증해야 한다. 실제 게임에서 대기방 감지가 검증됐거나 공식 명단 API가 확인된 것으로 가정하지 않는다.

### 명단 입력의 기본과 보조 방식 — 2026-09-16

**기존 기본 사양:** 최근 참여순으로 정렬한 클랜원 목록에서 직접 선택한다. 최근 참가자를 찾는 부담을 줄이는 기존 설계이며, 실제 선택된 출전 명단을 다음 판에 유지하는 것과는 구분한다.

최근 참여순 정렬과 선택된 출전자 유지의 이점은 구분한다. 추가 설명으로 **출전자 10명을 유지하고 라운드 사이에 변경된 사람만 교체하는 것이 기존 운영 방식**임을 확인했다. 이를 새 혁신 기능으로 제안하지 않으며, 수동 화면안은 이 운영 방식에서 찾기·교체 동작을 줄이는 데 집중한다.

**현재 코드와의 차이(2026-09-16 읽기 확인):** 최근 참여순은 기존 기획·목업에 있으나 앱의 명단 조회는 닉네임순이다. 결과 입력 후 기존 세션 명단은 남지만, 세션을 종료하고 새로 열 때 이전 선택은 복사하지 않는다. 상세 근거와 미반영 상태는 [Phase 2 현황](../TODO_Phase2.md)에 기록했다. 운영 DB 조회·브라우저 재현·수정은 이번 논의에서 수행하지 않았다.

대기방 연결의 프로젝트 적용 방향은 사용자 결정이며 구현·검증 완료를 뜻하지 않는다. 기본 활성화·플랜 범위·세부 UX는 별도로 정한다. PC 보조앱은 미채택 후보이고, 초성·별칭 검색은 수동 선택을 돕는 화면안이다.

**적용할 보조 기능: 대기방 연결**

1. 내전 시작 시 운영진이 웹에서 ‘대기방 연결’을 누르고 캡처할 게임 창을 선택한다.
2. 연결된 동안 화면이 대기방인지 판별하고, 닉네임 영역의 글자를 OCR로 읽어 해당 클랜 명단과 대조한다.
3. 운영진은 제안된 명단을 확인해 편성에 사용한다. 예: ‘등록된 멤버 10명 일치 · 확인이 필요한 이름 1개’.
4. 다음 판에는 ‘추가 1명 · 빠진 후보 1명’처럼 변경 부분을 제안한다. 현재 명단과 같으면 ‘명단 동일’로 표시한다.
5. 실제 출전 명단 반영·팀 편성 확정은 운영진이 한다. 변경 후보 확인을 기존 편성 화면에 통합해 별도 확인 모달을 매번 추가하지 않는다. 같은 명단이면 추가 선택을 생략한다. 화면에 보인다는 이유로 참가 의사·출전·퇴장을 자동 확정하지 않는다.

처리 흐름은 **선택한 창의 영상 → 대기방·닉네임 영역 판별 → OCR → 등록된 클랜원 대조 → 명단 후보 → 운영진 확인**이다. 창 연결은 화면을 얻는 단계이고 OCR은 그 화면의 글자를 읽는 단계다. 운영진의 반복적인 스크린샷 촬영·붙여넣기를 없애는 것이 목적이며, 첫 연결·오인식 수정·최종 확인은 남는다.

**제품 동작에서 지킬 구분**

- 대기방의 팀 슬롯과 관전자 영역을 구분해 출전자 후보만 제안한다. 관전자 등록·표시는 입력 화면 범위에서 제외하며 교대 대기자나 출전자라고 자동 판단하지 않는다.
- 게임 중·로딩·최소화·인식 실패로 명단이 사라져도 이탈로 처리하지 않는다. 마지막 확인 명단을 유지하고 새 판의 변경 후보와 구분한다.
- 여러 화면에서 일치한 이름만 안정된 후보로 제시한다. 동명이인·잘린 이름·OCR 오류는 확인 대상으로 남기고 임의로 계정을 연결하지 않는다.
- 화면 인식이 운영진의 수동 수정이나 진행 중 경기 명단을 덮어쓰지 않도록 한다.
- 권장 처리 구조는 음성 없이 게임 창의 필요한 영역을 운영진 기기에서 분석하고 서버에는 확인된 명단만 보내는 방식이다. 실제 처리 위치·성능·중단 UI는 기술 검증과 함께 정한다.

**기술적으로 확인한 것과 남은 검증**

- 웹에서는 `getDisplayMedia()`로 사용자가 고른 창의 영상 스트림을 얻을 수 있다. 따라서 연결 중 화면에서 명단 후보를 계속 갱신하는 실험은 가능하다. 새 캡처를 시작할 때마다 사용자 동작과 창 선택/승인이 필요하며, 권한을 영구 저장해 자동 재연결하는 것으로 설계할 수는 없다. [W3C Screen Capture](https://www.w3.org/TR/screen-capture/), [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia).
- 위 API의 존재가 오버워치에서의 성공을 보장하지는 않는다. 전체화면·창모드·최소화·브라우저 백그라운드, 해상도·언어·대기방 레이아웃, 닉네임 정확도, 게임 성능 영향을 검증해야 한다. 이번 논의에서는 실제 게임 캡처 실험을 하지 않았다.
- PC 보조앱은 Windows 창 캡처와 시스템 단축키 API로 연구할 수 있다. 게임 포커스·단축키 충돌·게임 환경 호환성은 별도 검증 대상이다. [Microsoft 창 캡처](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture), [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey).
- 게임 대기방 명단을 제공하는 공식 API는 이번 조사에서 확인하지 못했다. 게임 내부 API로 즉시 동기화할 수 있다는 전제는 두지 않는다.

**제3자 프로그램 정책 검토 — 2026-09-16**

- 제안 범위는 운영진이 선택한 창의 화면에서 명단 후보를 읽는 것이다. 게임 프로세스·메모리 접근, 코드 주입, 게임 파일 조작, 자동 입력·게임 내 팀 이동은 포함하지 않는다. 이 범위 제한이나 로컬 OCR 처리만으로 게임사의 허용·제재 면제가 성립한다고 볼 수는 없다.
- 블리자드는 외부 소프트웨어 사용이 라이선스 계약 위반일 수 있다고 안내한다. 오버워치 운영 정책은 허용하지 않은 이득을 주는 외부 프로그램 등을 제재 대상으로 설명한다. 이번 조사에서 **대기방 닉네임 OCR을 명시적으로 허용하거나 이 용도를 명시적으로 금지한 안내는 확인하지 못했다.** [외부 소프트웨어 안내](https://kr.battle.net/support/ko/article/13078), [오버워치 운영 정책](https://kr.battle.net/support/ko/article/76492).
- 확인 범위는 공식 검색 결과에 노출된 정책 본문이다. 현재 고객지원 페이지는 리디렉션 후 본문 추출이 되지 않아 최신 전체 조항의 대조에는 한계가 있다. 실제 감지 방식·제재 가능성도 확인하지 않았으며, 일반 화면 공유나 방송 도구 사용 사례로 허용을 추론하지 않는다.
- **연구 판단과 후속 결정:** 기술적 구현 가능성 검토 중 / 게임사 정책 적합성 미확인. 이후 사용자는 문의를 후속으로 두고 프로젝트 적용을 진행하기로 결정했다. 이전의 사전 문의 제안을 구현 착수 차단 조건으로 사용하지 않는다. 실제 문의·게임 캡처·구현은 수행하지 않았고 기존 최근 참여순 직접 선택이 기본이다.

**검증 기준:** 수동 선택 대비 첫 연결부터 명단 확인까지의 총 시간, 이후 판의 조작 수, 잘못 연결된 계정 수, 수정에 걸린 시간, 게임 성능 영향을 비교한다. 게임사 정책 확인은 별도 후속 항목으로 추적한다. 캡처 연동 자체가 더 번거롭거나 불안정하면 기본 선택 경로를 사용한다. 새 자동화 기능의 Free/Premium 경계는 미결이다.

### 수동 선택 화면안 — 2026-09-16

**설계 기준은 ‘좌우 5칸에 이름 클릭만으로 입력’이다.** 양 팀의 역할 순서는 위부터 **딜·딜·탱·힐·힐**로 고정한다. 입력은 **1팀 1~5번 → 2팀 1~5번**의 첫 빈칸 순서이며 사용자가 자리를 먼저 선택하지 않는다. 자리 우클릭으로 비우고 다른 이름은 그대로 둔다. **관전자 영역·등록은 제거한다.** 역할·입력 순서·우클릭 비우기는 사용자 확정 사항이다.

**기존 평가의 수정:** 현재 코드는 멤버와 팀·역할 슬롯을 함께 지정하는 구조다(`src/components/main-clan/clan-balance-roster-editor.tsx`). **추가는 고정 순서 첫 빈칸, 이미 배치한 사람의 이동은 직접 드래그**로 구분한다. 별도 자리 선택·교체 모드와 `이 자리 비우기` 버튼, 반복되는 현재 입력/이동/맞교환 표기는 두지 않는다. 이전의 맞교환 제외는 사용자의 직접 드래그 요청으로 변경했으며 별도 모드를 되살리는 것은 아니다. 실제 사용성 측정은 하지 않았다.

- **하단 후보 목록:** 체크·선택 색상·선택됨/미선택 범례를 모두 제거한다. 화면안에서는 이미 선택한 사람을 숨기고 나머지 이름을 최근 참여순으로 모아 보여준다. 명단에서 빼면 하단의 기존 정렬 위치에 돌아온다. 검색도 추가 가능한 사람만 대상으로 하며 미선택자를 관전자나 대기자로 해석하지 않는다.
- **숨김의 절충:** 후보 수가 줄고 중복 확인이 없어지는 대신, 선택 직후 목록이 당겨져 다음 이름 위치가 달라진다. ‘하단 목록 위치 고정’과 동시에 충족한다고 설명하지 않는다. 화면안에서는 같은 위치의 빠른 연속 클릭을 잠시 무시하는 보호를 넣었으며 실제 빠른 입력에서 유효한지는 검증이 필요하다. 보드의 위치와 순서는 유지한다.
- **공간 안정성:** 최근 참여순은 하단 후보에만 적용한다. 우클릭으로 비운 칸 외에는 사람을 옮기지 않으며, 새 이름은 항상 고정 순서상 첫 빈칸에 넣는다. 명시적인 드래그에서는 출발·도착 두 칸만 변경한다. 역할은 딜딜탱힐힐로 고정이다.
- **관전자:** 등록하지 않으며 입력 화면의 영역·등록 생략 문구·빈 관전자 칸도 두지 않는다. 기존 경기 진행 화면의 비출전자 관전 기능을 제거한다는 의미는 아니다. 미선택 클랜원을 관전자나 대기자로 자동 분류하지 않는다.
- **고정 역할 표시:** 각 팀 1·2번은 딜, 3번은 탱, 4·5번은 힐이다. 기존 편집 목업의 중앙 표시(딜 세로 막대 3개·탱 방패·힐 `+`)를 사용한다. 이 순서는 현재 앱의 `BALANCE_SLOTS`와도 같다. 앞선 ‘역할이 없는 원본 자리 입력’ 설명은 이 사용자 결정으로 대체한다. 자동 편성 시 최종 진영·역할 고정 조건과 OCR의 역할 매핑 검증은 별도로 정한다.
- **입력·반응:** 클릭 즉시 명단을 반영하고 매 클릭 서버 응답으로 조작을 막지 않는 안이다. PC 화면안에서 Delete/Backspace로 비우기, Alt+방향키로 인접 자리 이동·교환, Ctrl+Z로 되돌리기, `/`로 검색 초점을 제공한다. 검색창의 Delete·Ctrl+Z는 텍스트 편집으로 남긴다. 터치 길게 누르기 삭제는 드래그와 충돌하므로 제거하며 모바일 이동·삭제 조작은 별도 구체화한다.
- **명단 도구 배치:** 사용자 요청에 따라 되돌리기·리셋은 텍스트 버튼 대신 참여자 영역 우상단의 아이콘 두 개로 표시한다. 두 아이콘은 항상 같은 위치에 두고 툴팁과 접근성 이름을 제공한다. 되돌릴 내역이 없으면 되돌리기, 참여자가 없으면 리셋을 비활성화한다. 리셋은 모든 칸을 비우는 하나의 되돌리기 작업이며 별도 확인창을 두지 않는다.
- **OCR 합류:** 인식 결과도 원본의 팀·자리 위치에 맞춰 후보로 제시한다. 수동 수정·해제를 덮어쓰지 않고 같은 자리에서 확인할 수 있게 한다. 관전자·미확인 이름 때문에 현재 10명을 교체하지 않는다.
- **설명용 화면안:** 범례·선택자 숨김과 위 명단의 직접 드래그 이동/교환을 반영했다. 드롭 대상만 잠깐 강조하며 모드 버튼은 추가하지 않는다. 고정 역할·순서 자동 입력·우클릭 삭제를 유지한다. 0명/6명/10명 시작 상태를 비교할 수 있으며 실제 계정·저장·OCR·팀 편성은 연결하지 않았다.

**추가 편의성 후보 — 미확정**

1. **하단 후보를 교체할 칸에 바로 드래그:** 한 번의 드래그로 새 사람을 넣고 기존 사람은 하단으로 돌려보낸다. 현재 화면안은 위 명단끼리만 드래그하며 이 확장은 아직 구현하지 않았다.
2. **편집 초안 자동 복구:** 새로고침·탭 재진입 때 마지막 편집 명단을 복구한다. 실제 저장 범위·세션 구분·서버 변경과의 충돌은 구현 전에 정한다.
3. **검색 후 Enter 입력:** 결과가 한 명일 때만 Enter로 추가하고 검색창을 비우는 안. 여러 명일 때 임의 선택하지 않는다. 현재 초성 검색·`/` 초점 이동과 결합할 수 있다.

우선순위는 드래그 교체 → 초안 복구 → 검색 Enter를 제안한다. 추가 확인창이나 상시 모드 버튼은 늘리지 않는다.

**구체화할 질문**

- 적용할 ‘대기방 연결’에서 첫 연결과 변경 후보 확인의 부담을 어디까지 줄일까?
- 라운드 사이 출전자 10명 유지·교체에 맞춰 팀·역할 배치도 유지할까? 세션을 완전히 종료한 뒤에는 언제 이전 인원을 다시 불러올까?
- 인게임 닉네임과 등록 이름이 다를 때 초성·별칭 검색이 추가로 필요한가?
- 미가입자·게임 인증 전 구성원이 대기방에 있으면 경기 기록과 개인 계정을 어떻게 다룰까?
- 희망 역할은 기존 프로필·운영진 입력 중 무엇을 사용할까? 매 판 구성원에게 입력을 요구하지 않고도 편성 가능한가?
- 인원 미달·초과, 대기자·관전자, 중간 합류·이탈을 얼마나 간단히 표현할까? 접속한 사람과 실제 출전자는 어떻게 구분할까?
- 다음 판에 유지할 로스터·역할·밴 옵션과 교체 범위는 무엇일까?
- **밴픽:** 현재 웹 투표 흐름을 선택적으로 사용할지, 게임 안에서 정한 결과를 운영진이 기록하는 방식을 둘지 검토한다. 운영진의 참가자 대리 투표를 임의로 허용하거나 미접속자를 자동 동의로 처리하지 않는다. 이 부분이 정해지기 전에는 모든 내전에서 ‘구성원 웹 조작 0회’를 보장한다고 하지 않는다.
- 편성 담당자가 중도 이탈하거나 운영진이 동시에 조작하면 진행 권한을 어떻게 넘길까?

**연관 주제에 전달할 조건**

- `D-UX-02`: 홈의 내전 참가 버튼·별도 참가 대기실·첫 일정 만들기를 기본 절차로 전제하지 않는다. 운영진의 명단 반영과 진행 중 편성으로 이어지는 동선을 먼저 검토한다.
- `D-UX-05`: 모바일의 참가·준비 완료 버튼은 초기 후보다. 구성원이 웹을 열었을 때 얻는 선택적 가치와 실제 필요한 조작부터 다시 정한다.
- `D-UX-06`: 출전·참여 기록과 웹 방문 기록을 구분한다. 웹 미접속을 노쇼나 저참여의 근거로 사용하지 않는다.
- `D-UX-07`: 기본 참가 흐름에 별도 신청 절차가 필요하다는 가정으로 무료/유료 경계를 정하지 않는다.

**현재 상태:** 고정 역할·순서 입력·우클릭 삭제를 유지하며 범례 제거와 위 명단 드래그 이동/교환을 반영했다. 선택자 숨김은 후보 목록 압축의 영향을 함께 볼 화면안이다. 추가 편의성·모바일 조작·저장·자동화·밴픽·계정 요건은 `OPEN`이며 앱 구현과 기존 권한은 변경하지 않았다.

**관련 기준:** `D-EVENTS-01`, `D-PERM-01` / [이벤트](./pages/11-Clan-Events.md), [밸런스메이커](./pages/09-BalanceMaker.md), [S04](./slices/slice-04-balance-maker.md), [S06](./slices/slice-06-events-manage-store.md).

## D-UX-02. 역할별 홈과 첫 사용

**연동 메모:** 아래는 초기 화면 후보다. `D-UX-01` 피드백에 따라 내전 참가 응답·첫 일정·참가 대기실을 필수 절차로 전제하는 부분은 재검토한다.

**현재 관찰**

홈은 공지·규칙·일정·배지·MVP 중심이다. 실제 기록이 없는 클랜에서는 큰 빈 카드가 반복되고, 내전 100회·500회·1주년처럼 먼 목표가 먼저 보인다. 현재 빈 상태 안내는 구현되어 있으나, 첫 행동을 단계적으로 이끌어 주는 경험이 약하다.

**개선 제안**

| 상황 | 상단에 우선 표시할 내용 |
|------|--------------------------|
| 새 클랜 운영진 | 멤버 초대 → 첫 일정 → 첫 경기 기록 |
| 내전 준비 중인 운영진 | 참가 인원·부족한 역할·팀 편성·필요한 운영 업무 |
| 일반 구성원 | 다음 일정·참가 응답·배정된 팀 |
| 경기 진행 중 | 현재 경기와 바로 돌아가기 |
| 경기 종료 후 | 오늘의 결과·다음 일정 |

활동이 쌓이면 시작 안내를 평소 홈으로 전환한다. 초대 링크에서는 허용된 클랜 소개와 초대 목적을 보여 주고, 인증 후 원래 목적지로 이어지는 경험을 검토한다.

**구체화할 질문**

- 홈이 역할과 상황에 따라 바뀌어도 고정해야 할 정보는 무엇일까?
- 첫 사용 안내의 완료 기준과 다시 보는 방법은 무엇일까?
- 진행 중 경기와 곧 시작할 일정이 겹치면 무엇을 먼저 보여 줄까?
- 미가입자에게 공개 가능한 초대 정보와 가입·인증이 필요한 행동은 어디까지일까?

**관련 기준:** `D-AUTH-01`, `D-SHELL-01`, `D-PERM-01` / [클랜 홈](./pages/07-MainClan.md), [클랜 가입](./pages/06-ClanAuth.md), [S02](./slices/slice-02-game-clan-onboarding.md), [S03](./slices/slice-03-main-clan-shell.md).

## D-UX-03. 납득할 수 있는 팀 편성

**현재 관찰**

기획은 M/A 점수와 점수 차이·승률 예측을 판단 보조로 사용한다. 자동 편성·자동 점수 산정·승률 예측은 현재 미구현 범위다. ‘맵 밴’은 실제 규칙상 득표를 가중치로 최종 맵을 추첨하므로 이름과 행동의 의미가 다르다.

**개선 제안**

- 점수 차이와 함께 희망 역할, 같은 팀의 반복, 대기자 교대를 편성 조건 후보로 검토한다.
- 추천 근거와 조건 충족 여부를 짧게 설명한다. 예: ‘희망 역할 9/10명 반영 · 대기자 2명 교대’.
- 한 명을 교체했을 때 달라지는 조건을 확인하고 운영진이 조정할 수 있도록 한다.
- 점수·승률을 제공할 때 표본 수와 불확실성을 표현한다. 기록이 부족한 상태를 별도로 설계한다.
- ‘맵 밴’을 ‘맵 투표’로, M/A를 ‘운영진 점수/자동 점수’처럼 이해하기 쉬운 표현으로 설명하는 안을 검토한다.

**구체화할 질문**

- 반드시 지킬 조건과 가능한 한 맞출 조건은 무엇일까? 서로 충돌하면 무엇이 우선일까?
- 친구와 같은 팀, 반복 팀 방지, 역할 선호 중 어떤 요구까지 초기 범위에 포함할까?
- 근거·표본·수동 보정 이유를 본인·구성원·운영진에게 각각 얼마나 보여 줄까?
- 신규 참가자에게 점수가 없으면 어떻게 편성할까? 승률을 표시할 충분한 근거는 무엇일까?
- 운영진 수정과 이의 제기, 최종 편성 책임을 어떻게 다룰까?

**관련 기준:** `D-PERM-01`, `D-PRIV-01` / [밸런스메이커](./pages/09-BalanceMaker.md), [S04](./slices/slice-04-balance-maker.md). 설명 가능한 편성이 정확한 승률 예측을 보장한다는 뜻은 아니다.

## D-UX-04. 시각적 우선순위

**현재 관찰과 제안**

데스크톱 대시보드와 밸런스 화면을 직접 확인한 인상이다. 접근성 적합 여부를 전수 측정한 결과는 아니다.

| 관찰 | 개선 제안 |
|------|-----------|
| 배너 면적에 비해 행동 버튼이 작다 | 배너 높이를 조절하고 오늘 일정·현재 경기와 연결 |
| 카드의 배경·크기·강조 수준이 비슷하다 | 현재 할 일, 일반 정보, 과거 기록의 시각적 강도 구분 |
| 세션을 열기 전에도 빈 슬롯이 크게 보인다 | 시작 전에는 경기 준비와 참가자 확보를 우선 표시 |
| 목업의 플레이어 선택 영역이 화면 아래로 밀린다 | 편성 중 참가자 목록과 팀 보드를 함께 볼 수 있게 배치 |
| 메뉴는 접힌 아이콘 중심이고 점수에는 약어를 쓴다 | 메뉴 고정 펼치기와 의미가 드러나는 라벨 검토 |

**구체화할 질문**

- 각 화면에서 가장 먼저 보여야 할 정보와 가장 중요한 행동은 무엇일까?
- 항상 필요한 편성 도구와 접어 둘 고급 설정을 어떻게 구분할까?
- 노트북 화면에서 스크롤 없이 함께 보여야 하는 영역은 어디까지일까?
- 글자 크기·텍스트 대비·키보드 초점·터치 영역을 어떤 기준으로 검증할까?

**관련 기준:** `D-SHELL-01` / [클랜 홈](./pages/07-MainClan.md), [밸런스메이커](./pages/09-BalanceMaker.md), [목업 기준](../02-design/mockup-spec.md), [목업](../../mockup/pages/main-clan.html).

핵심 조작과 고급 설정을 구분하는 참고 원칙: [NN/g — Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/). 구체적인 배치는 실제 작업 흐름으로 검증한다.

## D-UX-05. 모바일 참가 경험

**연동 메모:** `D-UX-01`의 구성원 조작 최소화 방향에 따라, 아래 참가·준비 완료 버튼을 기본 필수 단계로 채택하지 않는다. 모바일에서 자발적으로 확인·참여할 가치부터 검토한다.

**검증할 사용 가정**

운영진은 PC로 편성하고 구성원은 휴대전화로 참가와 배정 결과를 확인할 수 있다. 실제 기기 사용 분포는 아직 조사하지 않았다.

**개선 제안**

- 참가·취소, 준비 완료, 내 팀·역할·맵 확인, 투표를 우선한다.
- 내 상태와 현재 필요한 행동을 화면 아래에 고정하는 구성을 검토한다.
- 운영 도구는 필요할 때 펼치되, 모바일 운영진의 사용 범위도 별도로 정한다.

**구체화할 질문**

- 모바일에서 팀 편성·교체·결과 입력까지 모두 지원할까?
- 참여자·대기자·관전자마다 기본 화면과 버튼이 어떻게 달라질까?
- 게임 중 재접속, 다른 탭 전환, 투표 마감, 연결 끊김 뒤 복귀를 어떻게 안내할까?
- 고정 버튼이 본문·키보드·초점을 가리지 않도록 어떻게 검증할까?

**관련 기준:** `D-SHELL-01`, `D-PERM-01` / [클랜 홈](./pages/07-MainClan.md), [밸런스메이커](./pages/09-BalanceMaker.md), [이벤트](./pages/11-Clan-Events.md).

<a id="ux-06"></a>

## D-UX-06. 함께한 기록과 공개 태그

**현재 관찰**

홈과 기획의 성취 표현은 승률·MVP·예측·코인 비중이 크다. 밸런스 기획에는 연패·슬럼프·노쇼 자동 태그가 있고, 경기 종료 결과는 일회성 팝업을 기본으로 한다. 태그는 기획된 항목이며 전체 자동 산정이 구현되었다는 의미는 아니다. 기존 경기 기록 열람과 별개로 ‘오늘 함께한 경험’을 돌아보는 흐름을 검토한다.

**개선 제안**

- 오늘 함께한 사람과 경기, 이번 달 참여한 날, 첫 내전, 클랜 공동 목표 등 참여 자체를 기념한다.
- 종료 팝업 이후에도 다시 볼 수 있는 오늘의 내전 요약과 다음 일정 연결을 검토한다.
- 공유 가능한 요약을 검토하되, 공개 범위는 별도로 정한다.
- 연패·슬럼프·노쇼를 공개 태그로 붙이는 방식은 재검토한다. 운영에 필요한 출석 정보와 공개적으로 축하할 성취를 구분한다.

공개 평가가 참여를 부담스럽게 만들 수 있다는 우려는 검증할 가설이다. 태그 제거·공개 범위 축소를 이미 결정한 것은 아니다.

**구체화할 질문**

- 일반 구성원이 다시 보고 싶은 기록은 무엇이며, 첫 성취는 무엇으로 정의할까?
- ‘오늘’의 집계 경계는 언제일까? 자정을 넘긴 내전을 어떻게 묶을까?

- 태그 유지·삭제·비공개 전환 중 어떤 방향이 적절하며, 기존 기록은 어떻게 처리할까?
- 기록 정정 시 요약·배지·통계에 어떻게 반영할까?

**관련 기준:** `D-ECON-03`, `D-ECON-04`, `D-PROFILE-04`, `D-STATS-02`, `D-PRIV-01` / [밸런스메이커](./pages/09-BalanceMaker.md), [통계](./pages/10-Clan-Stats.md), [프로필](./pages/14-Profile-Customization.md), [S05](./slices/slice-05-clan-stats.md), [S08](./slices/slice-08-player-profile-decorations.md).

## D-UX-07. 첫 방문 메시지와 Premium

**현재 관찰**

랜딩의 메시지는 ‘Archive Your History, Stay in Sync / 추억을 기록하고 클랜을 체계적으로 관리하세요.’다. PRD는 자동 편성·OCR·대진표·Discord 연동 등을 Premium으로 분류한다. 유료 결제와 여러 자동화 기능은 아직 별도 구현 범위다.

**개선 제안**

- 메시지 후보: **‘오늘 내전, 사람 모으기부터 팀 편성·기록까지.’**
- 실제 제공하는 기능으로 짧은 체험 흐름을 보여 주어 가입 전에 용도를 이해하게 한다. 위 메시지는 내전 참가 흐름이 구체화된 뒤 제공 범위와 맞춘다.
- Premium은 자동 편성·반복 운영·운영 자동화처럼 절약하는 시간으로 설명하고, 클랜 단위 혜택을 명확히 한다.
- 기본 참가 연결과 일정 전달을 무료로 어디까지 제공할지 재검토한다.

**구체화할 질문**

- 첫 방문에서 설득할 대상은 운영진일까, 일반 구성원일까?
- 구현된 기능만으로 보여 줄 수 있는 대표 체험은 무엇일까?
- 무료로 첫 내전을 끝내는 데 필요한 범위는 어디까지일까?
- 어떤 자동화에 지불 의사가 있으며, 이를 어떻게 확인할까?
- 무료/유료 경계를 바꿀 경우 기존 클랜의 사용 경험은 어떻게 전환할까?

**관련 기준:** `D-LANDING-01`, `D-EVENTS-03`, `D-NOTIF-02`, `D-STORE-02` / [PRD](./PRD.md), [랜딩](./pages/01-Landing-Page.md), [권한·플랜](./gating-matrix.md). 가격·알림 정책 변경은 아직 결정하지 않았다.

## 검증 방향과 범위

먼저 소규모 클랜의 운영진·구성원과 실제 내전 준비 과정을 확인한다. 게임 대기방에서 모인 뒤 웹 때문에 새로 생기는 행동과 운영진의 명단 입력 시간을 관찰한다. 게임 채팅·음성 등 기존 소통 수단을 쓰는 것 자체를 문제로 보지 않으며, 명단 반영·편성·기록의 반복 작업이 줄었는지 확인한다.

| 지표 후보 | 알고 싶은 것 | 측정 전 정할 기준 |
|-----------|---------------|-------------------|
| 첫 내전 완료 클랜 비율 | 새 클랜이 핵심 경험까지 도달하는가 | 대상 클랜·관찰 기간·완료 정의 |
| 다음 주 재사용 클랜 비율 | 한 번 사용한 뒤 다시 내전을 여는가 | 첫 완료 클랜 집단·다음 주의 기간 |
| 팀 편성 소요 시간 | 운영진의 준비 부담이 줄었는가 | 시작/종료 시점·인원 대기 시간 분리 |
| 구성원의 필수 웹 조작 수 | 게임 참가에 추가된 부담이 얼마나 되는가 | 최초 등록/반복 내전 구분·밴픽 사용 여부·선택적 열람 제외 |
| 첫 판 명단 반영·다음 판 변경 시간 | 운영진에게 입력 부담이 몰리지 않는가 | 수동 선택/OCR의 오류 정정 시간·명단 유지 시 합류/이탈 처리 |

측정 수단·목표 수치·자동 수집 여부는 미정이다. 실제 조사 결과가 나오면 기대 효과와 분리해 해당 주제에 반영한다.

게임·언어 확장, 꾸미기 상품 대량 추가, 순위·배지 증가, 복잡한 대회 형식은 초기 논의 순서에서 뒤에 두는 안을 제안한다. 스크림 승패 통계·클랜 간 대회·개인 이미지 업로드는 현재 범위 밖이며, 이 문서로 추가하지 않는다.

## 이어서 구체화하는 방법

1. 한 번에 위 코드 하나 또는 밀접한 두 개를 선택한다.
2. 해당 절에 사용자 상황, 후보안과 장단점, 정상/예외 흐름, 남은 질문을 추가한다. 새 요약 문서를 매번 만들지 않는다.
3. 결정된 내용은 `decisions.md`에 일자·근거·영향받는 기존 정책을 기록한다. 일부만 정해졌으면 남은 범위는 `OPEN`으로 둔다. 채택하지 않은 안도 이유를 짧게 남긴다.
4. 확정 범위의 페이지·슬라이스·PRD 등을 갱신하고, 화면안·구현·검증의 다음 작업을 구분한다. 결정되었다는 이유만으로 구현 완료로 표시하지 않는다.

**다음 논의 시작점:** `D-UX-01`에서 선택자 숨김과 직접 드래그를 구체화한다. 별도 자리 선택·맞교환 모드·반복 안내는 추가하지 않는다. 후보를 바로 끌어 교체하기·편집 초안 복구는 추가 편의성 후보다. 대기방 연결은 같은 명단 편집으로 합류시킨다. 구성원 웹 조작을 요구하는 밴픽은 별도 검토한다.

**논의 기록**

- 2026-09-16 — 초기 리뷰 제안 7개 등록. 사용자와 확정한 내용은 문서화 및 지속적인 구체화 방식이며, 개별 제품 정책은 미결이다.
- 2026-09-16 — 사용자가 즉흥적인 내전 참여와 웹 이용 자체의 부담을 지적했다. 실제 인원 확인 기준은 게임 내 대기방이라고 답했다. 사전 신청·체크인을 기본으로 제안한 초기 판단을 철회하고, 운영진 명단 반영·다음 판 재사용을 중심으로 수정안을 기록했다. `D-UX-01`은 OPEN을 유지한다.
- 2026-09-16 — 사용자가 클랜원 목록 선택을 기본 사양으로 확정하고 더 간단한 입력 방식을 요청했다. 대기방 연결·직접 선택 보조·PC 단축키 보조앱을 후보로 기록했다. 화면 캡처 API의 가능성과 제약을 확인했으며 실제 게임 검증·자동화 채택은 미결이다.
- 2026-09-16 — 사용자가 최근 참여순 정렬을 기존에 설계했다고 설명했다. 기존 정렬의 탐색 편의와 직전 판 선택 상태 재사용을 구분하고, ‘오늘 명단 유지’를 독립적인 혁신 기능으로 제안했던 표현을 정정했다.
- 2026-09-16 — 사용자가 창 연결의 제3자 프로그램 문제와 OCR 사용 여부를 질문했다. 화면 스트림·OCR·클랜원 대조 흐름을 명시하고, 공식 안내로 해당 용도의 허용 여부를 확정할 수 없어 게임사 정책 적합성을 미확인 사항으로 기록했다. 자동화 채택 결정이나 구현은 하지 않았다.
- 2026-09-16 — 사용자가 대기방 연결을 프로젝트에 적용하고 게임사 문의는 후속으로 진행하기로 결정했다. 수동 선택 UX를 함께 구체화하도록 요청했고, 기존 운영은 출전자 10명만 선택한 뒤 라운드 사이에 변경 인원을 교체하는 방식이라고 설명했다. 이를 기준으로 이름 연속 선택·10명 유지·직접 교체·OCR 후보 합류 화면안을 기록했다.
- 2026-09-16 — 사용자가 대기방 스크린샷으로 좌우 팀·위아래 순서가 유지되어야 수정 진행 위치를 놓치지 않는다고 설명했다. 출전자 1열 요약안을 대체하고, 게임과 같은 좌우 5칸·하단 관전자 구조를 반영했다. 입력 칸·변경 칸 표시와 자동 다음 빈칸·맞교환은 검토할 세부 동작으로 기록했다.
- 2026-09-16 — 사용자가 기존의 우클릭 비우기·1팀 1~5번 후 2팀 1~5번 자동 입력 방식과 선택 여부 가시성을 요구했다. 자리 선택·비우기 버튼·맞교환·반복 위치 표기를 제거하고, 체크/배경으로 하단 명단 상태를 구분하는 화면안으로 단순화했다.
