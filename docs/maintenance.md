# 로컬 파일·검증 산출물 정리

`.next`는 이 PC의 컴파일 결과·개발 캐시다. `.next-e2e*`는 포트별 검증 빌드다. Supabase QA 데이터베이스는 별도 서버에 있으며 이 폴더들을 정리해도 계정·클랜·게시글·코인은 삭제되지 않는다. 서버 중지 후 지운 빌드는 다음 실행에서 재생성된다.

## 캐시·검증 결과

`개발 시작`의 `npm run dev:qa`가 서버 실행 전에 자동 정리를 한 번 수행한다. 현재 QA 서버가 있으면 재시작하지 않고 재사용한다. QA 서버와 다른 Next 서버·빌드가 없을 때만 기존 개발 빌드 `.next`를 정리하고 서버를 실행한다. 프로세스·포트 조회나 정리 안전성을 확인하지 못하면 삭제와 서버 실행을 모두 중단한다. 빌드가 진행 중이고 QA 서버가 아직 없으면 서버 실행도 빌드 종료 이후로 보류한다.

Codex에서는 첫 호출부터 호스트 터미널(`exec_command`의 `sandbox_permissions: "require_escalated"`)을 사용한다. 제한 터미널에서 띄운 프로세스는 Next의 `Ready`가 표시돼도 호스트 브라우저에서 접속하지 못할 수 있다. 점검 실패 후 제한 환경에서 실행을 계속하던 우회 경로는 제거했다.

`dev:qa`는 새 서버와 재사용 서버 모두 `localhost`·`127.0.0.1`의 HTTP 응답 본문을 최대 60초 동안 확인한다. 두 주소가 모두 성공해야 `QA_HTTP_READY`를 출력한다. 이 표시 이후 내장 브라우저 두 탭을 열고 기존 로그인 세션을 먼저 재사용한다. 포트만 열려 있거나 한쪽 호스트만 응답하면 성공으로 처리하지 않으며 기존 프로세스는 보존한다.

Windows PowerShell 7에서 저장소 루트를 기준으로 실행한다.

```powershell
npm run clean:local
npm run clean:local -- -Apply
```

기본 명령은 삭제 대상만 보여준다. `-Apply`는 비활성 포트의 `.next-e2e`·`.next-e2e-숫자`와 오래된 Playwright 결과를 지운다. 삭제 직전 포트를 다시 확인하고 활성 서버의 빌드와 최근 1시간 내 캐시는 보존한다. 아직 포트를 열지 않은 Next.js 빌드가 실행 중이어도 중단한다. 알 수 없는 이름의 빌드 폴더와 링크 경로는 자동 삭제하지 않는다. 프로세스·포트 조회에 실패하면 삭제를 중단한다.

검증 결과는 기본 7일 보관하며 `.supabase-test`의 최근 결과 3개도 유지한다. `-ReportRetentionDays 1`처럼 보관 기간을 조절할 수 있다. 연결 정보·환경 파일·SQL·DB 타입·데이터 백업은 보존하며 `.supabase-test` 전체를 지우지 않는다.

개발 빌드 `.next`까지 정리하려면 QA 서버를 중지하고 다음을 실행한 뒤 `npm run dev:qa`로 재시작한다. 시드는 실행하지 않는다.

```powershell
npm run clean:local -- -Apply -IncludeDevBuild
```

## 소스·이미지·일회성 도구

- 컴포넌트는 import뿐 아니라 라우트 규약·동적 참조·테스트·문서까지 확인한 뒤 제거한다.
- 디자인 원본과 서비스 이미지는 용도가 다르다. 내용이 같은 사본만 해시로 검증하고 링크를 연결한 뒤 통합한다. 참조되는 검증 캡처는 유지한다.
- 재사용 가능성이 있는 샘플 보정 도구는 [QA 샘플 보관 폴더](../scripts/archive/qa-samples/README.md)에 둔다. 일반 개발·회귀 과정에서는 실행하지 않는다. 작업이 끝난 예시 꾸미기·프로필 사진 정리 도구와 전용 SQL은 제거했으며 과거 실행 내용은 Git 이력에서 확인한다.
- 로컬 사본을 지워 Git의 과거 이미지 용량까지 줄일 수는 없다. Git 이력 재작성은 별도 작업이며 이 정리에는 포함하지 않는다.

## 패키지 보안 업데이트

- 실제 업로드의 `sharp`와 Supabase 실시간 통신의 `ws`를 서비스 경로로, ESLint·CSS 처리기를 개발·빌드 도구 경로로 구분한다. 공용 UI는 `src/components/ui/`와 Base UI를 유지한다. 기존 shadcn CSS에서 사용하는 상태 규칙 6개·39줄만 [로컬 CSS](../src/styles/ui-variants.css)로 옮기고 [MIT 원문](../licenses/shadcn-MIT.txt)을 보존했다. 규칙의 `:where`·`false` 제외 조건과 탭의 그룹 방향 선택자를 유지한다.
- `package.json`의 제한된 `overrides`는 Supabase CLI의 `tar@7.5.21`, `@typescript-eslint/typescript-estree`의 `minimatch@11.0.1`에만 적용한다. 전자는 CLI·컨테이너 버전 변경 없이 설치 압축 해제를 수정하고, 후자는 수정판이 11부터인 패턴 증폭 문제를 차단한다. 전역 minimatch 교체는 기존 3 계열 호출 계약을 깨므로 사용하지 않는다. 상위 패키지가 수정판을 공식 채택하면 해당 override를 제거하고 설치·글롭 호출·린트를 다시 확인한다.
- 2026-11-06 CSS 분리 후 `shadcn`·`@shadcn/registry`·`deepmerge`와 전용 MCP/변환 도구 의존성을 제거해 npm 감사는 0건이다. `@ts-morph/common`이 사라져 그 override도 제거했다. `components.json`은 기존 UI 생성 규약을 보존하는 메타데이터이며 앱·검사·빌드는 CLI를 실행하지 않는다. 패키지를 다시 추가할 때는 도구의 하위 보안 경고까지 검토한다. - 부분 검증과 운영 반영 전 전체 검증은 [기존 기준](guides/agent-validation.md)을 유지한다. 감사의 버전 대조만으로 모든 공격을 재현·차단했다고 판정하지 않는다.

## SQL과 현재 구조

SQL 마이그레이션은 변경 이력이다. 현재 사용하지 않는 테이블을 생성했던 파일도 이후 제거 이력과 함께 유지한다. QA·운영의 적용 이력이 다르므로 적용된 파일을 삭제·재번호·임의 병합하지 않는다.

루트 `supabase/config.toml`의 `[db.seed]`는 `enabled = false`, `sql_paths = []`로 유지한다. 존재하지 않는 `seed.sql`은 참조하지 않으며 SQL 자동 시드를 실행하지 않는다. `db:seed`의 명시적 픽스처 도구와 `scripts/local-tests/config.toml`의 검사 전용 설정·데이터 준비 경로는 유지한다. 이 설정 정리를 적용하기 위해 DB 초기화·시드·서버 재시작을 실행하지 않는다. 마이그레이션·연결 정보와 활성 QA 데이터는 보존한다.

현재 앱이 기대하는 구조는 [DB 색인](02-design/database/current-schema.md)에서 확인한다. 생성 타입과 QA 구조를 동기화한 뒤 `npm run db:schema:index`로 갱신한다. 이 색인은 테이블·함수 목록이며 RLS나 함수 본문의 전체 SQL 덤프를 대체하지 않는다. 실제 적용 여부는 QA 마이그레이션 목록과 대조하고 운영 DB는 별도 승인 없이 변경하지 않는다.

### 마이그레이션 작성 단위

- **기존 이력 보존:** 2026-11-06 기준 마이그레이션 231개는 그대로 유지한다. 이번 기준은 앞으로 새로 작성하는 변경에 적용하며 기존 파일의 삭제·재번호·병합·내용 변경을 허용하지 않는다.
- **미적용 작업 묶음:** 아직 DB에 적용하지 않았음을 확인한 같은 작업의 테이블·함수·권한·데이터 보정을 한 파일에서 정리한다. 파일을 Git에 커밋했는지와 DB 적용 여부는 별개다. 같은 작업을 수정할 때마다 파일을 추가하지 않고, 서로 독립적인 작업이나 별도로 적용해야 하는 변경은 분리한다.
- **적용 여부 확인:** 해당 이력을 사용하는 로컬·QA·운영 등 DB의 적용 기록과 대조한다. QA에만 적용했고 운영에는 적용하지 않았어도 적용된 파일이다. 로컬 파일이나 Git 상태만 보고 미적용으로 판단하지 않는다. 확인할 수 없으면 기존 파일을 유지하고 후속 수정은 새 마이그레이션으로 추가한다.
- **적용 이후 수정:** 한 DB에라도 적용된 파일은 수정·삭제·재번호·병합하지 않는다. 새 파일에 후속 변경을 추가해 환경별 이력이 이어지게 한다.
- **묶은 SQL 검증:** 데이터 보정·권한·제약과 실행 순서를 보존하고, 허용된 격리 검사 DB에서 선행 이력부터 적용했을 때의 구조·데이터와 관련 회귀를 확인한다. 미적용 파일을 묶었다는 이유로 필요한 검증을 줄이지 않는다.

이력 확인·작업 단위 정리는 운영 DB 변경이나 활성 QA 데이터 초기화·재시드를 허용하는 지시가 아니다. 기존 QA/운영 적용·검증 기준과 보류 지시는 그대로 따른다.

자동 시작 경로·포트 보호·검증 결과 보관·백업 보존 회귀는 `npm run test:qa-startup`으로 확인한다. PowerShell 검증은 별도의 임시 폴더와 가짜 프로세스 목록을 사용하며 실제 서버나 DB를 변경하지 않는다.
