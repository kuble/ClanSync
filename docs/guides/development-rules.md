# 개발 작업 지침

공통 진입점은 [AGENTS.md](../../AGENTS.md), 변경 위험도별 검증 기준은 [자동 실행·검증 범위](agent-validation.md)다. 이 문서는 해당 작업이 있을 때 필요한 절만 읽는다. 최신 기능·권한·플랜 정책은 페이지 명세와 [결정 기록](../01-plan/decisions.md)을 기준으로 하며 오래된 도구 설정을 정책 근거로 사용하지 않는다.

## 협업과 Git

- 에이전트가 구현·검증·의미별 커밋과 현재 작업 브랜치 푸시를 담당한다. 사용자의 명시적인 보류 지시를 우선한다. 커밋 기준은 [AGENTS.md](../../AGENTS.md)의 나노 커밋 규칙을 따른다.
- 다른 브랜치의 변경을 `main`에 반영하는 PR 작성·병합 준비·병합·직접 푸시 전에는 사용자 확인을 받는다. 확인 전에 변경 요약·브랜치·PR 제목과 본문 초안을 검토 가능한 상태로 준비한다. 이미 승인된 범위는 다시 묻지 않는다.
- 현재 브랜치가 이미 `main`이면 위임된 커밋·푸시 기준을 따른다. Git 연결에 따른 자동 빌드와 별도 수동 배포를 구분하며, 수동 배포는 명시 요청이 있을 때 수행한다.
- 기존 사용자 변경은 보존하고 이번 작업 커밋에 섞지 않는다. 필요할 때만 작업 브랜치를 만들며 환경의 브랜치 명명 규칙을 따른다.

## 의사결정

- `OPEN` 정책과 새 enum·권한·상태 전이·알림 정책·데이터 모델 등 번복 비용이 큰 선택은 사용자 확인 후 확정한다.
- 선택이 필요한 경우 2~4개 옵션과 장단점·권장안을 제시한다. 답을 받기 전에는 그 결정에 의존하는 명세·스키마·목업·DB를 변경하지 않는다.
- 확정한 선택은 기존 `decisions.md`의 해당 결정과 관련 명세에 날짜·사용자 확인 근거를 기록한다. 결정 확정 커밋에는 `DECIDED (YYYY-MM-DD, 사용자 컨펌)`을 명시한다.
- 이미 확정된 요구의 구현, 순수 버그·오타·링크·형식 수정, 로컬 개발 설정과 명시적으로 위임된 선택에는 확인을 반복하지 않는다. 위임받아 선택한 사항은 결과에 요지를 짧게 남긴다.

## 코드 작성

- Server Component를 우선하고 상호작용이 필요한 경계에만 `'use client'`를 둔다. Next.js API·파일 규약은 설치된 `node_modules/next/dist/docs/`를 먼저 확인한다.
- 도메인과 props 타입을 명시하고 `any`를 피한다. Props 타입은 컴포넌트 가까이에 둔다. Supabase 반환 오류를 처리하고 사용자·권한 경계와 RLS를 유지한다.
- 기존 `src/components/ui/`의 공용 컴포넌트를 우선 사용한다. 파일명·코드 구조는 해당 디렉터리의 현재 관례를 따른다. 변수명은 영어, 새 주석과 사용자 문구는 한국어를 기준으로 한다.
- `page.tsx`, `layout.tsx`, `route.ts` 등 라우트 규약을 지킨다. JSON 응답에는 기존 프로젝트의 `NextResponse.json` 패턴을 따른다.
- 현재 화면·스타일은 `src/`와 `public/`, 기능 기준은 최신 페이지 명세를 따른다. 제거된 Phase 1 정적 목업은 Git 이력으로만 확인한다.

## 기능 명세 동기화

- 입력·검증·오류·저장 후 처리, 로딩·빈 상태·권한 분기, 진입·이동·완료·이탈 흐름이 의미 있게 바뀌면 `docs/01-plan/pages/`의 해당 명세를 같은 작업에서 갱신한다.
- 여러 페이지가 영향을 받으면 각 관련 명세에 반영한다. 변경 내역의 반복보다 최종 동작 기준을 적는다.
- 현재 초점은 `docs/TODO.md`, 상세 구현·검증은 `docs/TODO_Phase2.md`, 이력은 `docs/TODO_LOG.md`에 둔다. 작은 문구·스타일 변경마다 진행도·회고를 복제하지 않는다.

## 직접 검수 안내

- 새 라우트·주요 UI·인증·권한·가드의 도입 또는 의미 있는 변경, 마일스톤 완료, 사용자 요청 시에는 [QA 시나리오](../QA_시나리오.md)에 최신 절차를 위에 추가한다. 자동 검사가 이 안내를 대신하지 않는다.
- UI·동작 변화가 없는 문서 수정·리팩터·의존성 갱신은 생략할 수 있다.
- 한 줄 검증 목적, 실제 환경 URL·브랜치, 사전 조건, 번호별 조작과 기대 화면, 기대 결과 2~5개, 실패 시 확인할 지점 1~2줄을 적는다.
- 사용자 QA는 `localhost:3011`의 운영진과 `127.0.0.1:3011`의 멤버 세션을 구분한다. 자동 검사는 전용 로컬 DB·3010 서버를 사용한다. [픽스처 안내](../01-plan/debug-and-fixtures.md)와 [검사 실행법](../../e2e/README.md)을 따른다.
- 실제 로그인과 허용된 테스트 계정으로 재현하며 URL 쿼리의 인증·권한 우회를 안내하지 않는다. 활성 QA 명단에 시드를 다시 실행하지 않는다. Preview URL이 있으면 실제 전체 주소를 제공한다.

## 개발 시작

- `/개발시작`과 `개발 시작`은 [AGENTS.md](../../AGENTS.md)의 `dev:qa`·HTTP 확인·내장 브라우저 두 탭 절차를 따른다.
- 기존 서버를 포트 번호만으로 강제 종료하거나 검사에 사용자 QA 서버를 재사용하지 않는다. 검증은 [위험도별 기준](agent-validation.md)에 맞춰 수행한다.

## 진행도와 인계

- 사용자가 현황 갱신이나 인계를 요청하거나 주요 작업을 마치고 종료할 때 현재 코드·관련 명세·검증 결과를 대조한다. 실제로 확인하지 않은 항목은 완료로 표시하지 않는다.
- 관련 라우트·권한·데이터 규칙과 현재 Phase 2 진행도를 확인한다. Phase 1 기록은 과거 설계 근거가 필요한 경우에만 참조한다. 전체 기획·완료 이력을 매번 읽지 않는다.
- 상태가 의미 있게 바뀐 경우에만 TODO의 날짜·현재 초점, Phase 2의 관련 항목, 세션 로그를 짧게 갱신한다.
- 다음 작업은 미해결 권한·데이터 정합성 → 미완료 검증 → 후속 기능 순으로 정하고, 필요한 파일·남은 검증·보류 사항을 포함한 다음 작업 프롬프트 한 개를 남긴다. 응답은 결과와 다음 행동을 짧게 전달한다.
