# 페이지 로딩 병목과 개선 우선순위

2026-11-06, 보안 의존성 정리 후 현재 작업 브랜치 기준. **조사·후보 정리 단계이며 제품 코드·DB·캐시·배포는 변경하지 않았다.** 스택 변경보다 전체 이력 전송·반복 조회·페이지 진입 때의 부수 작업을 줄이는 것이 우선이다. 아래 순위는 비용 구조·노출 범위·검증 난도를 함께 고려한 것이며 개선율을 실측한 순위는 아니다.

## 검증 근거와 한계

- [기존 전수 조사](page-performance-audit-2026-11-06.md)의 37개 페이지·58개 상태를 재검토했다. 그때의 개발 모드 코드량·온라인 QA 본문 지연을 현재 운영 성능으로 해석하지 않는다. 이미 끝낸 요청 내 인증 재사용·관리 패널 분리·내전 점수 스트리밍은 새 개선 후보로 중복 집계하지 않았다.
- 현재 Next 16.4.5의 새 프로덕션 빌드에서 전용 로컬 DB의 임시 2인 클랜으로 7개 경로를 각 3회, 총 21회 측정했다. [식별자 없는 원본 표본 CSV](page-loading-bottlenecks-2026-11-06.csv). 각 경로 첫 방문과 후속 방문을 포함하며 완전히 새로운 서버/브라우저의 cold start 실험은 아니다.
- 서버 fetch를 계측해 로컬 Supabase 요청의 이름·시각·메서드·상태만 기록했다. 요청 구간의 후속/백그라운드 작업이 포함될 수 있으므로 아래 API 횟수를 SQL 문장 수나 모두 직렬 실행되는 횟수로 해석하지 않는다. 병렬 요청의 시간은 단순 합산하지 않는다.
- LCP 관측은 일부 표본에서 수집 시점이 빨라 미완료였다. 0ms나 정상 통과로 집계하지 않았다. INP·실사용 p75/p95·모바일 CPU 제한·운영 네트워크는 측정하지 않았다. 표본 3개로 p95를 주장하지 않는다.
- `2026-11-06T12-26-54-390Z-21183617`: 측정 1개와 기존 계정/권한 격리 2개, 총 3개 통과. 전용 데이터는 계정·클랜·경기 각 0건으로 정리됐다. 임시 계측 도구·테스트는 제거했다. 제품 코드와 전체 검증 명령은 유지한다.

| 경로 | TTFB 중앙값 | 본문 완료 중앙값 | 초기 JS decoded | 후속 방문의 서버 API 요청 |
|---|---:|---:|---:|---:|
| 게임 선택 | 38ms | 95ms | 974KiB | 9회 |
| 대시보드 | 42ms | 135ms | 1,076KiB | 40회 |

작은 로컬 데이터에서는 이 경로의 50ms 이상 long task가 관측되지 않았다. 이것이 큰 데이터·느린 기기의 CPU 병목 부재를 뜻하지는 않는다. 온라인 QA의 이전 4~11초 지연과 이 빈 클랜 수치를 직접 비교해 개선율을 계산할 수 없다.

## 우선순위

### 1. 대시보드의 전월 MVP 계산에 필요한 데이터만 조회

- 근거: [대시보드 로더](../../src/lib/clan/load-clan-dashboard.ts)는 전체 수동 경기·완료 내전을 500개씩 순차로 읽고 `normalizeClanMatchRecords` 뒤에 전월을 필터링한다. 승부예측 조회는 이미 회차 시작 월로 필터링하므로 전체 이력 문제와 구분한다. [페이지 로더](../../src/lib/clan/load-dashboard-rows.ts)는 매 페이지 정확한 전체 개수도 요구한다. 작은 클랜에서도 대시보드 전체 측정 구간의 서버 API는 후속 방문 40회였다.
- 비용: 전체 경기 수 M, 경기당 참가자 P라면 전송/정규화 입력이 O(MP)로 증가한다. 전월 통계 몇 줄을 보여 주는 비용이 전체 누적 이력에 종속된다.
- 후보: 이미 있는 통계 조회 모델의 전월 집계를 활용하거나, 동일한 정규화 규칙을 보존한 서버 집계로 MVP의 최소 결과만 반환한다. 정확한 회차 통계 5회 조회도 단일 그룹 집계로 묶는 것을 함께 검토한다. 목표는 월/구성원 규모의 결과를 반환하며 전체 원본을 앱 서버로 가져오지 않는 것이다.
- 통과 조건: 원본 로더와 신규 결과를 KST 월 경계·동률·최소 경기 기준·무승부/무효·수동 기록과 내전 연결·정정/삭제·멤버/운영진별로 대조한다. 권한 확인 후 최소 집계 DTO만 반환하며 서비스 권한의 원본 기록을 클라이언트로 전달하지 않는다. 기존 집계의 정의가 다르면 단순 교체하지 않는다.

### 2. 내전 준비의 전체 점수 이력·분석 재생을 줄이기

- 근거: [점수 로더](../../src/lib/balance/load-balance-score-data.ts)의 `readScoreHistory`는 첫 500개 뒤 두 페이지씩 병렬로 끝까지 읽는다. 최신 역할 점수 몇 개를 채울 때도 전체 JSON 이력이 필요하다. 경기 진행 중 완성 스냅샷·점수 비공개 상태의 우회 경로는 이미 최적화됐고 유지 대상이다.
- 현재 로더의 최소 모의 행으로 확인한 요청/크기/처리 경과: 100건=1회·18KiB·2ms, 1,000건=3회·179KiB·3ms, 10,000건=21회·1,787KiB·20ms. 모의 처리에는 행 생성·크기 측정용 직렬화도 포함한다. DB/네트워크와 프리미엄 예측 학습을 제외한 작은 모의 행이므로 실데이터 처리 시간으로 일반화하지 않는다. 실제 이력 JSON은 기존 QA 표본에서 500건당 약 655~664KiB였다.
- 후보: 사람/역할별 마지막 유효 점수를 서버에서 한 번에 선택해 반환한다. 예측 모델에는 전체 사건 순서가 필요하므로 점수 조회 축소와 별도로 정산 시점 기준의 체크포인트/증분 계산을 검토한다. 현재 [예측 계산](../../src/lib/balance/analysis-prediction.ts)은 시작/정산 사건을 정렬해 재생하고, DB의 `balance_prediction_basis`도 과거 사건을 순회한다. 단순히 최근 N경기만 잘라서는 동일한 모델이 되지 않는다.
- 통과 조건: 계정/게스트 연결·역할별 최신값·동일 시각 정렬·겹치는 방·현재 스냅샷 우선·비공개/Free 점수·정정/삭제 시 재계산을 참조 결과와 대조한다. 전체 이력 노출 범위를 확장하거나 RLS를 우회해 속도를 얻지 않는다. 체크포인트 설계는 별도 검증 전 적용 보류다.

#### ‘다음 단계’ 지연의 구간별 재측정

2026-11-06 사용자 요청으로 현재 Next 16.4.5 개발 서버에서 계측했다. 공유 QA에서는 기존 클랜에 만든 **별도 임시 정규 방 한 개의 10명 고정 편성**을 한 번 확정했다. 기존 방을 초기화하거나 시드를 실행하지 않았다. 전용 로컬 DB에서는 임시 10인 클랜의 같은 흐름을 3회 측정했다. [식별자·인증값을 제외한 구간별 CSV](balance-next-step-timing-2026-11-06.csv).

재조회에서는 공통 레이아웃/페이지의 사용자·컨텍스트 Promise를 요청 안에서 재사용한다. 같은 Promise를 기다린 두 소비자의 시간을 중복 합산하지 않았다. 재조회 619.1ms 안에 로그인·권한 재확인이 포함되므로 표의 개별 항목도 모두 합산하지 않는다. 보조 조회 중 권한 RPC는 85.0ms, 승부예측 풀은 115.1ms, 명단 풀은 156.5ms였고 병렬 그룹 전체는 157.3ms였다.

이번 표본에서 **창 전환의 필수 경로 중 큰 구간은 화면 재조회 619ms와 저장 왕복 300ms**였다. 전체 응답을 길게 만든 것은 배경 점수·분석 처리다. 이전에 분석 RPC를 붙잡아도 창이 열리는 검사를 통과했고, 이번 로컬 브라우저에서도 클릭 → 창 DOM 생성이 553.1/632.9/665.1ms였다. 이 로컬 수치를 공유 QA의 실제 표시 시간으로 대체하지 않는다.

처음 관측한 12.1초 전체 요청과 같은 느린 표본은 이번 단발 QA 측정에서 재현되지 않았다. 당시 Proxy 2.4초를 순수 로그인 시간으로, 액션 2.2초를 순수 DB 저장 시간으로 해석할 수 없으며 당시 지연의 세부 분해는 남아 있지 않다. 과거 일시적 지연의 특정 쿼리·제공 자원 원인까지 확정하지 않는다.

최종 로컬 검사 `2026-11-06T13-23-17-850Z-6339c7f6`에서 한 시나리오의 3회 측정이 통과했고 종료 후 계정·클랜·경기는 모두 0건이다. 응답 완료를 기다리던 계측 초안의 시간 제한 실패 표본은 제외했다. QA 임시 방 잔여 0건과 기존 방 ID 보존을 확인했다. 임시 계측·테스트는 제거하고 제품 소스 5개를 계측 전 내용으로 복구했다. 기능·스키마·배포 변경은 없다.

후속으로 편성 저장 성공 응답을 현재 패널에 직접 반영해 맵 유형 창을 여는 전환의 전체 페이지 재검증을 제거했다([구현·최종 검증](../TODO_Phase2.md#2026-11-06-편성-확정-응답으로-맵-유형-창-열기)). 위 표는 수정 전 측정이며 수정 후 공유 QA의 부하 측정이나 개선율 계산은 반복하지 않았다.

### 3. 공통 RSC 요청 안의 조회 합치기와 부가 영역 대기 분리

- 근거: [클랜 레이아웃](../../src/app/games/[gameSlug]/clan/[clanId]/layout.tsx)은 컨텍스트·알림·네임카드·이모티콘·웰컴 상태를 함께 기다린다. [공통 컨텍스트](../../src/lib/clan/load-main-clan-context.ts)와 [통계 로더](../../src/lib/clan/stats/load-clan-stats.ts)가 같은 요청에서 클랜/소속/권한 설정을 다른 투영으로 다시 읽는다. 통계 측정에는 소속 RPC 2회·설정 2회·클랜 2회가 관측됐다.
- 후보: 이미 사용하는 요청 한정 `React.cache` 스냅샷을 필요한 필드까지 통합해 재사용한다. 로그인·소속/권한은 먼저 확정하고, 알림/꾸미기 등 부가 응답은 고정 높이 영역 안에서 따로 완성한다. 병렬 호출 수를 늘리는 것보다 중복과 필수 경로의 대기 단계를 줄인다.
- 통과 조건: 요청/계정/클랜/권한 간 공유 금지, 권한 변경 뒤 다음 요청의 최신 값, 액션 실행 시 새 권한 검사, 로딩/실패 중 화면 높이·기존 컨트롤 보존. Proxy와 RSC의 Auth 호출은 서로 다른 경계이므로 단순 중복으로 보고 삭제하지 않는다.

### 4. 배지 조회 때 실행되는 쓰기 요청 분리

- 근거: [배지 로더](../../src/lib/clan/load-clan-badges.ts)는 표시할 때 취소 대상 DELETE → 획득 UPSERT → 조회를 순차로 실행한다. 이번 서버 추적에서 해당 테이블의 DELETE·POST·GET이 각각 8회였다. 실제 변경 행 수나 WAL 쓰기는 측정하지 않았고, 매번 행이 변경된다고 주장하지 않는다.
- 후보: 표시 경로를 읽기 중심으로 만들고, 획득 조건을 바꾼 이벤트의 확정/정정 처리와 배지 정합성 갱신을 연결한다. 변경 감지·재검증이 먼저이며 비동기로 넘기기만 하는 방식은 사용하지 않는다.
- 통과 조건: 최초 획득일·새 배지 표시·정정 시 취소·대표 배지 무효화·중복/동시 이벤트·탈퇴/삭제와 장애 복구가 동일해야 한다. 실제 DB 이벤트 설계가 필요하므로 1·3보다 적용 위험은 높다.

### 5. 경기 기록 회차 번호의 N+1 COUNT 제거

- 근거: [기록 로더](../../src/lib/clan/stats/load-clan-stats.ts)의 `addArchiveSessionNumbers`는 표시할 회차 K개를 조회한 뒤 각 회차 이전의 정규 회차 수를 별도로 센다. 네트워크 요청은 1+K회이며 같은 이력 범위를 반복 집계한다.
- 후보: 클랜의 정규 회차를 `(opened_at, id)`로 순서화한 단일 결과에서 필요한 회차만 반환한다. DB 실행 계획에 따라 윈도 함수 또는 이미 검증된 회차 번호 조회 모델을 선택한다. HTTP 요청 수 O(K)→O(1)이 목표이며 DB 처리까지 O(1)이라고 주장하지 않는다.
- 통과 조건: 같은 시작 시각의 ID 순서·정규/깜짝 구분·정정/삭제·기간 경계·다른 클랜 차단. 현재 `(clan_id, opened_at)` 계열 인덱스가 이미 있으므로 누락 인덱스라고 단정해 추가하지 않는다.

### 6. 초기 표시와 무관한 통계·프로필 UI 코드 지연 로딩

- 근거: 현재 프로덕션의 초기 스크립트 decoded 크기는 약 974~1,311KiB다. [통계 화면](../../src/components/main-clan/clan-stats-experience.tsx)은 첫 HoF 탭에서도 다른 통계/기록/설정 컴포넌트를 정적으로 import한다. 관리 화면의 패널 분리는 이미 끝난 작업이다.
- 후보: 현재 사용하지 않는 탭·편집 창을 클라이언트 경계에서 분리한다. 실제 네트워크 요청/coverage와 느린 모바일 CPU에서 확인된 묶음부터 선택한다. 큰 파일이 빌드 폴더에 있다는 사실만으로 초기 다운로드 병목으로 판정하지 않는다.
- 통과 조건: 직접 링크·선택/초안 유지·키보드/터치·불러오기 실패/재시도·테마·서버/클라이언트 비밀값 경계. 현재 로컬 표본에서 긴 브라우저 작업이 없으므로 서버/데이터 후보보다 우선순위는 낮다.

## 보안과 측정의 적용 기준

- 기존 계정 동시 격리·권한 변경 반영·잘못된 권한 설정 거절 검사는 통과했다. **구현하지 않은 개선안의 보안까지 확인된 것은 아니다.** 각 후보는 위 정합성·보안 조건을 통과한 뒤 적용한다.
- [Next 데이터 보안](https://nextjs.org/docs/app/guides/data-security)은 서버의 권한 검사·최소 DTO·요청 안의 재사용을 안내한다. 인증/개인별 데이터를 공용 `use cache`·LRU·CDN에 넣는 제안은 제외한다.
- [Supabase SSR 인증 안내](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs&queryGroups=framework)는 검증된 `getClaims`와 최신 사용자 조회인 `getUser`를 구분한다. 로컬 서명 검증의 이점은 비대칭 키 사용 여부에 달려 있고 최신 사용자/세션 상태 의미도 달라진다. 키 변경·로그아웃/삭제 반영을 검증하지 않은 인증 교체는 보류한다. `getSession`의 사용자 객체를 신뢰하는 단축은 제외한다.
- [조회 계획 분석](https://supabase.com/docs/guides/database/query-optimization)·[RLS 성능](https://supabase.com/docs/guides/database/postgres/row-level-security-performance)에 따라 실제 계획·버퍼·정책 비용을 확인한 뒤 인덱스/집계를 선택한다. 공개 Data API의 explain 설정은 정보 노출 위험 때문에 켜지 않고, 로컬/허용된 서버의 읽기 계획만 사용한다. 이번에는 운영/QA의 실행 계획이나 자원을 새로 조회·변경하지 않았다.
- [Next prefetch 안내](https://nextjs.org/docs/app/guides/prefetching)는 미리 읽기 때 렌더 부수 효과가 실행될 수 있음을 설명한다. 현재 배지 갱신·활동 기록·초대 발급 경로를 점검하기 전에는 모든 링크의 prefetch를 일괄 활성화하지 않는다.
- [LCP 최적화 안내](https://web.dev/articles/optimize-lcp)처럼 실사용 지연과 로컬 측정을 구분한다. 향후 동일 데이터/역할/네트워크에서 기본 구현과 후보를 교대로 측정하고, 요청·전송량·본문 완료·주요 컨트롤 준비·오류율을 함께 비교한다. 줄어든 비용이 관측되지 않거나 권한/정합성에 차이가 있으면 채택하지 않는다. 운영 반영 전 전체 `test:all` 범위를 유지한다.

현재 권장 착수 순서는 **대시보드 전월 집계의 참조 결과 대조 → 내전 이력의 반환량 축소 설계 → 공통 요청 재사용**이다. 운영 데이터의 실제 조회 계획·동시 사용자 부하·DB I/O 예산은 미확인이므로 요금제/자원 증설이나 수치 개선율은 제안의 전제로 두지 않는다.
