# 실패 검사 로컬 재현과 병목 비교

후속: 아래 재현에서 남은 실패 66건은 수정 후 모두 통과했다. 이 문서는 최초 재현의 수치·원인을 보존한다. [66건 수정·최종 통과 근거](failed66-recovery-2026-11-05.md).

2026-11-05 KST. 온라인 QA 데이터는 그대로 두고, 전용 로컬 DB를 검사 묶음마다 초기화했다. 브라우저는 worker 1·재시도 0으로 실행했다. 운영 반영은 하지 않았다. 이전 브라우저 실패 142건은 최종 **76 통과·66 실패**이며 미실행·건너뜀은 없다. 이번 로컬 재현에서 남은 주요 지연은 화면 요소 대기였고, DB 요청 시간 초과는 재현되지 않았다.

## 범위와 측정

- 이전 브라우저 실패 142개 목록에서 이미 로컬 재검증한 로그인·프로필 이동 2개를 제외하고 나머지를 기능별 10묶음으로 선정했다. 같은 줄에서 생성되는 매개변수 검사는 함께 실행한다.
- DB 실패와 관련된 9개 파일을 승부예측/정산, 회차/자동 종료/선호, 엠블럼/공개 범위/공지의 3묶음으로 실행했다.
- 검사 전후 PostgreSQL 누적 통계, 요청 실행 시간, I/O 시간, 함수 실행 시간을 비교했다. 테스트 데이터 준비와 종료 후 전체 정리는 비용 비교에서 제외하며, 브라우저 묶음은 앱 빌드·시작을 포함한다.
- 초반 계측은 새 연결에만 I/O 시간이 적용될 수 있었다. 이후 전용 서버 설정을 다시 읽혀 기존 연결과 WAL 기록/동기화까지 측정했다. `new-connections-v1`인 초반 결과를 완전한 I/O 측정으로 사용하지 않으며 DB 세 묶음은 보완된 계측으로 다시 확인했다.
- `pg_stat_statements`는 실행에 실패한 요청을 모두 포함하지 않는다. 실패 로그·브라우저 trace·10초 간격 활동 관측을 함께 확인한다. 관측 사이의 짧은 대기를 모두 포착한다고 주장하지 않는다.
- 실시간 전송용 `walsender`가 오래 실행 중인 요청으로 표시되던 계측을 수정했다. `activityScope=client-backend-v1`인 관측에서만 화면 요청의 최장 실행 시간을 해석한다. 누적 DB I/O 통계에는 이 수정의 영향이 없다.

## 확인된 실패 원인

최초 10묶음의 실패 trace 69개에서 로컬 HTTP 요청 15,470개를 비교했다. 1초를 넘긴 응답은 로그인 페이지 GET 약 2.01초와 랜딩 GET 약 1.72초 두 개였다. 기록된 Server Action 요청의 최대 응답은 약 281ms였다. 이 수치는 실패 trace에 남은 요청의 관측값이며, 모든 기능·사용자의 최대 응답 시간을 뜻하지 않는다. 테스트 준비용 Node 요청은 별도 DB 통계로 확인했다.

- `balance-history-current.spec.ts:8`: 종료 시각만 PC의 현재 시각으로 넣고 시작 시각은 DB 기본값으로 생성한다. 시작이 종료보다 약 2.7ms 늦어 `balance_session_series_time_ck`에 걸렸다. 느린 조회가 아니라 테스트 데이터의 시간 조건 오류다.
- `balance-insights`, `balance-lobby:325`, `balance-role-team-review`, `balance-roster-dock`: 검사에서 점수의 `점` 접미사 또는 이름의 `#태그`를 본문에 기대하지만 현재 화면은 숫자·이름을 간결하게 표시한다. 원래 실패한 단계는 기대한 표시와 현재 화면의 불일치이며 DB 시간 초과가 아니다.
- `balance-auction-flow`: 편성 시작의 특정 Server Action 요청을 20초 기다린다. 실패 trace에서 검사 조건과 일치하는 시작 요청은 확인되지 않았고, 확인된 다른 내전 요청은 약 121ms에 응답했다. 화면 행동/검사 경로를 추가 확인할 항목이다.
- `clan-emoji-composition`: 댓글 버튼 클릭에 약 176.7초를 사용했다. 실제 코드는 넓은 화면에서 마우스를 올리면 댓글 창을 열고 버튼을 숨긴다. trace에서도 열린 창이 클릭을 가로막은 뒤 숨겨진 버튼을 반복 대기했다. DB 응답을 기다린 3분이 아니다. 데스크톱 hover·키보드·터치 경로를 나눠 검사해야 한다.
- `clan-promotion:12`: 이미 바뀐 테마 전환 버튼의 `title`을 찾는 데 약 176.4초를 사용했다. 요청 지연이 아닌 선택자 대기다.
- 일부 API 401은 검사 환경의 원인을 확인했다. 프로덕션 모드 로그인은 `Secure` 쿠키를 설정한다. 설치된 Playwright의 `Cookie.matches`/`filterCookies`는 HTTP `localhost`만 예외로 인정하고 `127.0.0.1`의 보안 쿠키를 API 요청에서 제외한다. trace에서 브라우저 요청에는 인증 쿠키가 있고 별도 API 요청에는 없는 것을 확인했으며, 값이 없는 모형 쿠키로 두 호스트의 판정 차이를 재현했다. 검사 주소만 `localhost:3010`으로 수정하고 인증 API·관련 실패 검사를 추가 재검증했다. 앱의 쿠키 보안을 완화하지 않았다.
- `clan-board-viewport`의 높이 5,249px 대 기대 상한 1,005px, 사진 배치 비율, 깜짝 내전 점수 등은 별도 기능·계약 검토 대상이다. 모든 실패를 오래된 검사로 처리하지 않는다.

## 온라인 QA와 비교

온라인에는 테스트 데이터 생성·수정·삭제를 하지 않았다. 기존 60초 Metrics 수집과 네 번의 읽기 전용 통계 스냅샷만 사용했다. 온라인의 I/O 시간 계측 설정은 변경하지 않았다.

- 13:03:14~13:04:40 KST의 86.735초 동안 업무 DB의 블록 읽기·행 추가·수정·삭제 증가는 0이었다. 자동 종료와 예약 방 생성은 각각 1회, 약 9.7ms·9.1ms였다. 두 순간의 일반 연결은 모두 idle이었다.
- 13:06:51~13:08:09 KST의 77.75초도 블록 읽기와 행 변경 증가는 0이었다. 예약 작업은 각각 2회, 총 22.9ms·20.7ms였다. 이 구간은 현재 업무 조회 병목의 증거가 아니다.
- 진단 조회 자체도 비용이 있었다. SQL 본문까지 읽는 통계 조회 2회가 총 2.12초·임시 쓰기 16.61MiB를 만들었다. SQL 본문을 생략한 다음 조회는 약 242ms·1.80MiB였다. 두 쿼리의 구성도 달라 정확한 A/B 실험은 아니며, 통계 수집을 무부하로 간주하지 않는다. 반복 로컬 수집은 `pg_stat_statements(false)`로 변경했고 온라인 전체 요청 통계의 반복 수집은 추가하지 않았다.
- 온라인 디스크 지표는 시스템 전체 장치의 활동을 포함한다. DB 블록 읽기와 같은 값이 아니며 WAL·외부 통계 파일·시스템 작업의 비용도 따로 봐야 한다. 이번 자료만으로 과거 Disk IO Budget 경고의 단일 원인이나 예산 회복을 확정하지 않는다.

장기 누적 통계는 2026-09-15 KST부터 여러 코드 버전과 검사 작업이 섞여 있다. 비용 위치를 좁히는 참고 자료다.

| 요청 형태 / 객체 | 누적 호출 | 평균 실행 | 해석 |
|---|---:|---:|---|
| `public.balance_sessions` 조회 형태 1 | 97,394 | 113ms | 반복 조회량을 먼저 확인할 후보 |
| 내전 방·회차·세션 결합 조회 | 1,290 | 670ms | 많은 기록을 가진 로컬 자료로 따로 재현할 후보 |
| `public.read_balance_analysis_context` | 6,210 | 224ms | 현재 프런트의 직접 호출이 검색되지 않아 과거 비용 신호로만 보관 |
| `public.get_clan_namecards` | 17,978 | 63ms | 새로고침 시 중복 호출과 자료량 영향을 구분할 후보 |

이 표의 평균과 이번 작은 임시 자료의 평균 차이를 최적화 효과로 계산하지 않는다.

## 근거와 한계

- 완료된 검사 실행 17회(초기 DB 3, 브라우저 10, 인증 보정 1, 보완 DB 3) 모두 종료 후 로컬 계정·클랜·경기 0건을 확인했다. 같은 DB 검사를 두 번 실행한 수를 별도 시나리오로 더하지 않는다.
- 계측·현황 단위 검사 9개, 변경 검사 설정·새 회귀의 ESLint와 각 브라우저 묶음의 프로덕션 빌드를 통과했다. 사용자용 QA 3011과 현황 3040을 유지했다.
- 남은 66개는 정상으로 처리하지 않았다. 우선 오래된 선택자·hover/클릭 경로·잘못된 시각의 준비 데이터를 정리하고, 공개 범위·점수·레이아웃 단언은 현재 명세에 맞춰 기능 문제인지 검토해야 한다. 이후 많은 경기 자료를 가진 로컬 환경에서 내전 조회 비용을 따로 확인할 필요가 있다.
- 이전 전체 회귀의 미실행 29개·건너뜀 9개까지 이번 작업으로 검증한 것은 아니다. 전체 통과 전 운영 반영 보류를 유지한다.

원시 실행·오류·trace와 `db-before.json`, `db-after.json`, `db-comparison.json`은 `.local-tests/runs/`에, 시계열은 `.local-tests/metrics/2026-11-05.jsonl`에 보관한다. SQL 본문과 입력값은 계측 파일에 저장하지 않는다. 최초 실패 목록·묶음 선택·집계는 `.tmp/recheck-failed-tests.json`, `.tmp/local-recheck-manifest.json`, `.tmp/local-recheck-summary.json`이며, 최신 결과 대조는 `.tmp/local-recheck-reconciliation.json`이다. 온라인 비교 근거는 `.tmp/qa-counters-comparison.json`·`.tmp/qa-light-comparison.json`, 네트워크 집계는 `.tmp/local-network-summary.json`이다.

이 결과는 작은 임시 데이터와 PC 자원에서의 재현이다. 온라인 QA의 과거 I/O 예산, 당시 누적 데이터량·백그라운드 작업까지 같게 재현하지 않았으므로 과거 경고 원인이나 온라인 회복을 확정하지 않는다.
