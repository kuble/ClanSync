# ClanSync 알파 점검 · 2026-10-16

대상은 **1개 클랜, 계정 100명 이하**다. 실제 화면·코드·QA DB와 당일 공식 자료를 검토했다. 가격은 실제 청구서가 아닌 예산이며, 법률 검토는 특정 구현의 적법성이나 게임 계정 안전을 보증하는 의견서가 아니다. 운영 DB·배포·플랜 구매는 실행하지 않았다.

클릭 가능한 디자인 목록과 비용 계산기는 같은 폴더의 `index.html`이다. `node scripts/serve-alpha-review.mjs`로 실행한 뒤 [점검 보드](http://127.0.0.1:3040/)를 연다. 화면 링크는 로그인된 QA 리더의 `localhost:3011`을 사용한다. 모달 항목은 페이지를 연 뒤 목록에 적힌 버튼을 누른다. 회원용 호스트는 `127.0.0.1:3011`이다.

## 2. 성능: 도입한 변경과 검증

### 이번 변경

1. **로비: 변경 알림 + 합치기 + 보완 조회.** 기존 5초마다 전체 RSC 재조회 대신, 이미 publication에 포함된 방·반복 예약·참석 응답의 INSERT/UPDATE를 구독한다. 120ms 안의 이벤트를 한 번으로 합치고 렌더 중에는 후속 조회 하나만 예약한다. 보완 조회는 30초, 숨김·오프라인 탭은 조회하지 않으며 복귀 시 다시 읽는다. 삭제·멤버 정보 변경·소켓 실패는 보완 조회로 복구하므로 최장 약 30초의 지연이 가능하다. 네트워크 실패 자체에는 상한 시간이 보장되지 않는다.
2. **지연 로딩.** 경기 설정·안내 코드를 `next/dynamic`으로 분리해 실제로 열 때 읽는다. 서버의 권한 검증·저장 시 재검증은 유지한다.
3. **공통 클랜 레이아웃의 존재 확인.** 빨간 점 표시용 `count(exact)`를 `LIMIT 1`로 바꿨다. 정확한 인원수·가입 대기 수처럼 실제 숫자가 필요한 조회는 유지했다. 클랜 ID 필터·RLS·요청 단위 React cache도 유지했다.

관련 공식 근거: [Next.js 지연 로딩](https://nextjs.org/docs/app/guides/lazy-loading), [Supabase 변경 구독과 필터·RLS·규모 한계](https://supabase.com/docs/guides/realtime/postgres-changes), [PostgreSQL LIMIT](https://www.postgresql.org/docs/current/queries-limit.html). 구독은 페이지에 표시된 최대 100개 방으로 제한한다. 새 테이블·공개 API·공유 사용자 캐시·service role 브라우저 전달은 추가하지 않았다. 삭제 이벤트의 RLS 한계를 피하기 위해 새 구독에서는 DELETE를 받지 않는다.

### 측정

로컬 Windows → QA Supabase, Next 16.2.0 **프로덕션 webpack 빌드**, 별도 3010 서버, Chromium, QA 리더. 각 경로 5회 탐색, 전후 빌드는 동일 환경을 사용했다. 첫 실행·네트워크 편차와 일부 병행 QA 부하가 있어 통계적 A/B 실험은 아니다. JS는 응답 body의 **압축 해제 크기 합계/5**이며 청구용 전송량·고유 chunk 용량과 다르다. TTFB는 HTML 첫 바이트이며 LCP·INP·전체 데이터 표시 완료 시간이 아니다.

| 화면 | 첫 화면 JS 전 → 후 | HTML TTFB 중앙값 전 → 후 |
|---|---:|---:|
| 내전 로비 | 1,280,291 → 1,196,032 bytes (**−82.3KiB, −6.6%**) | 138 → 94ms |
| 관리 / 내전 | 1,107,580 → 1,108,988 bytes | 99 → 81ms |
| 클랜 통계 | 1,132,916 → 1,138,560 bytes | 85 → 109ms |
| 이벤트 | 1,026,013 → 1,027,417 bytes | 117 → 89ms |

모든 화면이 빨라졌다고 해석하지 않는다. 통계 TTFB는 오히려 늘었고 공통 chunk의 소폭 증가도 있다. 확실한 결과는 내전 첫 JS 감소와 유휴 전체 조회 감소다. 변경이 없는 로비의 주기 조회는 시간당 **720 → 120회(83.3% 감소)**이며 초기 연결·복귀·실제 이벤트 조회는 별도다.

RLS를 적용한 실제 QA 쿼리 1회씩에서 count는 10.420ms·버퍼 hit 651, LIMIT은 10.656ms·hit 645였다. 열린 경기가 적은 현재 상태에서는 차이가 측정 오차 수준이다. 불필요한 전체 개수 계산을 없앤 구조 개선이며 ‘DB 몇 배 가속’ 근거는 없다. 기존 인덱스를 확인했고 중복 인덱스를 추가하지 않았다. [실행계획 확인 지침](https://supabase.com/docs/guides/database/debugging-performance), [쿼리·인덱스 최적화](https://supabase.com/docs/guides/database/query-optimization).

원시 측정은 `measurements.json`, 재현 명령은 `verification.md`에 있다. 100명 동시 부하와 실제 배포 리전의 p95·LCP·INP·Supabase 청구 사용량은 아직 측정하지 않았다.

| 이미지·꾸미기·배지·프로필 | 스크린샷·배너의 업로드 픽셀/용량 상한과 썸네일 파생본을 우선 검토. 변환 서비스는 별도 과금이므로 무조건 활성화하지 않는다. 이미지 크기·LCP 실측 후 적용. |

알고리즘 선택 기준은 **측정 → 적은 행 읽기 → 요청 합치기 → 필요한 코드만 전송 → 인덱스/요약**이다. Postgres Changes도 이벤트×구독자 수만큼 권한 확인 비용이 생긴다. ‘실시간은 무료’나 ‘인덱스는 많을수록 좋다’는 전제를 두지 않는다. 변경 규모가 커질 때만 인증된 private Broadcast·읽기 모델·keyset을 비교한다.

## 3. OCR·오버레이: 도입 판단

**알파에는 경기 종료 화면을 사용자가 선택해 로컬 OCR → 사람이 확인 → 내전에 반영하는 방식이 적합하다. 상시 오버레이는 별도 검증 후 결정한다.** 브라우저 기능과 데스크톱 오버레이는 다른 제품·배포 범위다.

Embark의 공식 FAQ는 플레이 간섭·불공정 이점이 없어야 한다고 조건을 붙인다. 이것을 오버워치 허가로 볼 수 없다. [Embark 공식 FAQ](https://id.embark.games/arc-raiders/support/faq/167-common-anti-cheat-questions).

## 4. 100명 알파의 비용·수익

### 가격과 운영 전제

실결제 기능은 `clan-manage-subscription-panel.tsx`에서 ‘준비 중’이고 현재 플랜 전환은 테스트다. 따라서 **현재 확인 가능한 제품 수익은 0원**으로 잡는다. 월 9,900원/클랜은 기획 문서의 가격 가설이며 결제 상품으로 확정된 가격이 아니다. 알파 100명을 100개의 유료 고객으로 계산하지 않는다.

계획 환율은 **1달러=1,500원**이며 실시간 환율 예측이 아니다. 공급사 표기는 USD이고 부가세·카드 환전 비용이 추가될 수 있다. 아래 원화 예산에는 해외 서비스 세금 예비비 10%를 보수적으로 넣었다. 세무 유형에 따른 공제·의무는 별도 확인 대상이다.

### 사용량 가설과 관리 포인트

100계정, 피크 동시 20명(최대 100명까지 별도 부하 검증), 월 8회×2시간×시청자 20명=320 viewer-hours를 기획 가정으로 둔다. 매번 5초 갱신이면 월 230,400회, 30초 보완 조회면 38,400회에 실제 변경 조회가 더해진다. RSC 1회 50KiB라 가정하면 이 부분만 약 11.0→1.8GiB다. **이 50KiB는 비용 민감도 가정이며 실측 응답 크기가 아니다. Vercel 응답량과 Supabase DB egress를 같은 값으로 합산하지 않는다.**

Realtime도 1회 변경이 20명에게 전달되면 20메시지가 된다. 예를 들어 월 2,000변경×20명=40,000메시지지만 알파 내전 투표·프레임 단위 OCR까지 방송하면 훨씬 늘 수 있다. 이미지 원본·로그·DB 저장, 메일 발송 급증, 비정상 호출이 MAU 숫자보다 먼저 예산을 압박할 수 있다. QA DB 전체 크기는 진단 시 약 91MB였으며 테스트 경기·다른 픽스처도 포함하므로 운영 DB 성장률로 환산하지 않는다.

Supabase Free 기준 DB 500MB·저장 1GB·egress 5GB·Realtime 동시 200/월 200만 메시지다. 100명이 두 탭을 열면 동시 연결 상한에 근접할 수 있고 다른 클라이언트도 합산된다. MAU 100이 요금제의 사용자 한도보다 작다는 사실만으로 성능·비용 여유를 보장할 수 없다. Pro의 기본 제공량 안에 들어갈지는 대시보드의 **실제** egress/CPU/메시지·연결 수로 확인한다.

표는 고정비를 유지한다는 민감도 계산이지 50개 클랜을 현재 서버로 검증한 판매 예측이 아니다. 현금 손익분기는 유료 **12개**다. 월 운영 20시간×시급 2만원을 추가하면 고정비 50만원, 손익분기는 **60개**다. 유료 전환율을 전체 활성 클랜의 20%로 가정하면 각각 활성 60개·300개가 필요하다. 이 전환율은 시장 조사로 검증하지 않았다.

지원이 유료 클랜당 월 20분만 들어도 약 6,667원이다. 기여액 8,403원 대부분이 사라진다. 초기에는 운영진의 일정 등록·명단 정리 시간을 얼마나 줄이는지가 사업성의 핵심이다. 개발 시간을 제외해도 알파 운영 8–20시간/월을 2만원으로 평가하면 월 16–40만원의 시간 비용이 더 생긴다. 1개 클랜에서는 광고나 구독으로 이를 회수한다고 가정하지 않는다.

광고·스폰서 수익은 보장된 트래픽·계약이 없어 **0원**으로 예산을 잡는다. 코인 상품의 개발용 전환을 현금 매출로 세지 않으며 환금·승패 연동 유료화는 현재 모델의 수익원에 포함하지 않는다. OCR 호출료보다 자체 오버레이 개발·업데이트·지원의 시간 비용이 훨씬 커질 수 있어 별도 투자안으로 분리한다.

### 경영 판단: 4주 알파

- 목적: 시장 규모 예측보다 한 운영진이 반복해서 쓰는지와 데이터 신뢰를 확인한다. 무료 알파, 월 현금 상한 10만원을 기본으로 둔다(유료 QA 포함 시 12만원).
- 1주: 초대·재접속·예약·참석·내전 종료·정정·백업 복구 동선을 확인. 실제 분 단위 알림 워커 연결과 custom SMTP가 필요하다.
- 2–3주: 최소 4회 내전, 주간 재사용 멤버 비율, 운영진 준비 시간 전후, 수동 복구 건수, 권한 문제, 20명 동시 상태 반영 지연을 기록한다.
- 4주: 운영진 준비 시간 30% 절감·4회 중 3회 이상 재사용·기록 유실 0건을 내부 통과 기준으로 제안한다. 이후 다른 운영진 3명에게 월 9,900원/19,900원 가치를 인터뷰한다. 이 수치는 목표이지 달성 결과가 아니다.
- 투자 우선순위: 알림·예약 신뢰성과 입력 시간 절감 → 디자인 D1/D2 → 수동 선택 OCR 실험 → 검증된 유료 수요 이후 상시 오버레이. 확정 계약 없이 외부 메시지를 보내거나 플랜을 구매하지 않았다.
