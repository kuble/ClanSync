# 경기 기록 저장 후 조회 실패 추적

## 확인한 원인

기록 저장 트랜잭션 실패와 저장 후 조회 실패는 별개였다. 기존 `loadClanStatsSource`는 소속 RPC의 오류를 확인하지 않고 빈 소속으로 처리했다. 액션은 저장 후 날짜 목록과 선택 날짜를 각각 조회했고, 둘 중 하나가 `null`이면 “조회 권한이 변경됐다”고 반환했다. 실제 권한이 유지돼도 일시 통신 오류가 같은 안내를 만들었으며 편집 창에는 다시 저장하는 버튼이 남았다.

- 일반 편집 시나리오를 8회 순차 반복한 실행 `2026-11-05T10-00-58-214Z-d7211e0a`는 6 통과·2 실패였다. 임시 진단에서 클랜·설정 조회는 HTTP 200, `select_my_clan_membership`만 502인 응답을 확인했다. 두 실패의 원인이 모두 같다고 단정하지 않는다.
- 변경 전 실행 `2026-11-05T10-10-17-909Z-6d5f1f8e`에서 실제 저장 커밋 직후 소속 조회에만 502를 주입했다. 저장된 기록이 있는데도 기존 권한 오류와 열린 편집 창이 재현됐다.
- 변경 후 일반 반복에서도 자연 발생한 502를 확인했다. 로컬 Kong 로그를 초기화 전에 직접 읽었으며, 10:26:46 UTC의 소속 조회에서 `upstream prematurely closed connection while reading response header from upstream`이 확인됐다. API 서버(PostgREST)가 응답 헤더를 보내기 전에 연결이 종료돼 게이트웨이가 502를 반환한 경로다. 같은 시점 앱은 `DB_READ_RETRY` 후 정상 조회했다.
- 해당 로컬 Kong·PostgREST·DB 컨테이너의 재시작 횟수는 모두 0, OOM 종료는 모두 false였다. 연결 종료의 내부 원인까지 확정한 것은 아니며 온라인 QA의 Disk I/O 경고와 인과관계가 입증된 것도 아니다. 초기화가 컨테이너 로그를 없애므로 위 로그는 당시 확인한 핵심 문구를 기록한 것이다.

## 변경

1. 읽기 전용 요청에서 일시 통신·서버 오류만 150ms 후 한 번 재시도한다. SDK 재시도를 꺼 총 두 번으로 제한하며 인증·권한·잘못된 입력·취소는 재시도하지 않는다. 실패한 조회의 위치·상태 코드만 기록하며 원문 응답·토큰·사용자 데이터는 로그에서 제외한다.
2. 조회 오류와 실제 소속/권한 없음을 구분한다. 저장 후에는 현재 권한을 한 번 확인하고 날짜 목록·선택한 날의 기록을 함께 읽어 중복 조회를 줄인다.
3. 저장 이후 조회가 계속 실패하면 저장 완료 상태와 오류를 함께 반환한다. 입력·저장 버튼을 잠그고 **기록 다시 불러오기**로 전환한다. 이 액션은 로그인과 현재 권한을 다시 검사한 뒤 조회만 실행한다. 생성·수정·삭제 RPC를 자동으로 재실행하지 않는다.

## 로컬 검증

전용 API `127.0.0.1:55431`, 사이트 `localhost:3010`, worker 1·Playwright 자동 재시도 0을 사용했다. 기존 3011·온라인 QA DB에는 시드·수정·삭제를 수행하지 않았다. DB 스키마 변경은 없다.

| 검사 | 결과/근거 |
|---|---|
| 조회 재시도·권한/취소·진단 로그 단위 검사, 격식체 | 6 통과 |
| 변경 파일 ESLint·타입 검사 | 통과 |
| 최초 복구 검사 | 3 통과·1 검사 단언 실패, `2026-11-05T10-19-47-953Z-5d3d59b5`: 열린 모달이 가린 바깥 영역을 검사하던 선택자를 응답 확인으로 변경 |
| 관련 회귀·일반 편집 8회 반복 | 36 통과·1 검사 단언 실패, `2026-11-05T10-23-31-003Z-afd2e065` |
| 권한 해제·복원 최종 확인 | 1 통과, `2026-11-05T10-29-55-598Z-b616e3c3` |
| 프로덕션 빌드 | 로컬 E2E 실행에 포함, 통과 |

관련 회귀의 남은 단언은 브라우저 UI의 권한 차단 안내가 정상인데 테스트 도구의 응답 본문 한글 디코딩이 달라 실패했다. UI 안내와 응답의 `ok:false`, 기록 데이터 부재를 검사하도록 보정했다. 실제 권한을 해제한 채 조회를 재시도한 후 복원하며, 저장 요청 횟수가 계속 1인지 확인한다.

최신 결과는 **관련 시나리오 30개·37회 실행 모두 통과**다. 37회에는 기존 기록 편집 시나리오 8회 반복이 포함되며, 마지막 권한 검사는 위 별도 실행 결과로 대체한다. 신규 복구 6개는 일시 소속 조회 오류, 지속 소속/기록 조회 오류, 실제 권한 해제·복원, 삭제 후 읽기 실패, 로그인 만료를 확인한다. 기록 추가와 삭제 모두 커밋 후 저장 RPC 호출이 1회임을 검증했다.

관련 37회 회귀 구간(238.7초)의 DB 임시 쓰기와 데드락은 모두 0이었다. 읽기 시간 3.319ms·쓰기 시간 8.584ms이며 연결 종료를 디스크 포화로 결론 내릴 근거는 없다. 이 수치는 해당 로컬 표본이며 온라인 QA의 회복 여부를 뜻하지 않는다.

진단·재현·검증 5회 모두 종료 후 전용 DB 계정·클랜·경기 0건과 검사 잠금 해제를 확인했다. 사용자 QA 서버 3011은 실행 상태를 유지했고 정리 도구의 추가 삭제 대상은 없었다. 각 실행의 `events.jsonl`, `output.log`, `db-comparison.json`과 실패 추적 파일은 `.local-tests/runs/{실행 ID}/`에 있다. 일반 편집을 8회 반복한 임시 검사 파일은 검증 후 제거했다.

오류 주입은 테스트 서버의 Node preload에서만 실행된다. 전용 로컬 주소·검사 모드·실행 폴더 안 제어 파일이 모두 일치해야 작동하며 제품에는 오류 주입 경로나 클라이언트 스위치를 추가하지 않는다. 임시 클랜의 실제 저장 응답 이후만 오류를 넣어 저장 실패를 조회 실패로 가장하지 않는다.

집중 재실행:

```powershell
node --test scripts/read-query.test.mjs scripts/ui-formal-copy.test.mjs
npm run test:e2e -- e2e/clan-match-record-read-recovery.spec.ts e2e/clan-match-record-editing.spec.ts e2e/clan-stats-read-model.spec.ts
```

전체 브라우저·DB 회귀를 이번에 재실행한 것은 아니다. 공유 QA·운영 적용과 배포는 보류한다. 기존 쓰기 최적화와 전체 DB 회귀 결과는 [이전 보고서](stats-write-optimization-2026-11-05.md)를 참조한다.
