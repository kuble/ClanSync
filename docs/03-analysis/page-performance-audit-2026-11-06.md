# 전체 페이지 성능 조사 — 2026-11-06

맵 유형 선택이 과거 경기 점수와 분석 모델을 기다리던 경로를 분리했다. 관리 화면의 불필요한 초기 스크립트를 줄이고 공통 인증·가입 상태 조회의 중복과 순차 대기를 줄였다. QA DB의 응답 편차가 커서 전체 페이지의 응답 시간이 일괄 개선됐다고 판정하지 않는다.

## 측정 범위와 해석

- `src/app/**/page.tsx` 37개를 목록화하고 관리 10개 탭·게시판 분류/상세·진행 중 내전·게임 ID 재등록·계정 탭을 포함한 58개 진입 상태와 대조했다. [전체 58행 CSV](page-performance-audit-2026-11-06.csv)에 원본 파일·본문 완료·초기 스크립트 크기·가장 긴 브라우저 작업을 남겼다.
- QA 3011 개발 서버, Chromium 1304×884, 기존 리더와 별도 비로그인 브라우저로 측정했다. 시드·게임 기록·명단·잔액 변경은 하지 않았다. 홍보 화면의 기존 초대 링크 자동 발급 등 화면 진입 자체의 동작은 실행된다. 사용자의 두 내장 브라우저 탭은 이동·재시작 없이 유지했다.
- 변경 전 최초 순회 `before.json`, 따뜻한 캐시 순회 `before-warm.json`, 변경 후 두 순회 `after.json`은 `.local-tests/performance/`에 저장했다. CSV는 변경 전 따뜻한 순회와 변경 후 두 순회를 비교한다. 개발 컴파일·외부 DB/네트워크·실시간 QA 진행 상태가 달라지는 관측값이며 통제된 A/B 실험이나 운영 성능 보장이 아니다.
- `bodyMs`는 탐색 시작부터 HTML/RSC 본문 수신 완료, `loadMs`는 load 완료, `scriptKiB`는 초기 탐색 시 수신한 **압축 해제 후** 스크립트 크기다. 개발 도구·HMR을 포함하며 운영 번들/압축 전송량으로 해석하지 않는다. 나중에 여는 모달·탭의 추가 스크립트는 별도다.
- 외부 Discord 입장 경로는 초대 발급을 피하려고 변경 후 측정에서 제외하고 구현만 확인했다. 초대·참가자 연결의 두 토큰 페이지는 만료 토큰 상태, 커뮤니티 글 상세는 없는 글 상태로 측정했다. 모든 유효 토큰·게시물·권한 상태를 검증한 결과가 아니다. 변경 전 최초 순회에는 Discord 경로가 포함됐으며 이후 측정기는 제외한다.
- 변경 후 1회차의 `/games/[gameSlug]`는 정상 리다이렉트 중 측정 문맥이 교체돼 측정기 오류 1건이 났다. 2회차는 측정 성공이다. 도구는 이후 예상 도착 주소를 기다리도록 수정했다. 다른 오류를 정상 성공으로 집계하지 않았다.

## 병목과 수정

### 공통 진입

게임 게이트는 게임 조회를 마친 뒤 본인 프로필·소속을 읽었다. 기존의 본인 게임별 소속 RPC를 사용해 세 조회를 병렬로 시작한다. 게임 선택·프로필/엠블럼·클랜 찾기·커뮤니티/글 상세·초대/참가자 연결 등 9개 서버 페이지는 요청 안에서 클라이언트와 인증 사용자를 재사용한다. 서버 액션의 새 인증 조회와 계정/권한 격리는 유지하며 요청 간 사용자 데이터를 캐시하지 않는다.

### 관리 초기 코드

서버 컴포넌트가 관리용 클라이언트 패널을 한꺼번에 참조해 선택하지 않은 편집기·차트도 초기 코드에 포함했다. 클라이언트 경계의 `next/dynamic`으로 14개 패널을 분리했다. 서버 렌더·현재 탭 데이터 조회와 권한 검사는 그대로다.

|---|---:|---:|---:|
| 운영 현황·멤버 | 10,509KiB | 7,230KiB | 31.2% |

모두 개발 모드의 초기 decoded 크기다. 홍보를 열 때는 해당 편집기 코드가 실제로 필요하다. 관리 권한·전체 메뉴·구형 플랜 주소/뒤로가기 검사를 통과했다.

### 내전과 맵 유형 선택

기존 내전 요청은 완료 경기 1,282개의 점수·명단을 세 번 순차 조회했다. 직접 읽기 표본은 500행 527ms/655KiB, 다음 500행 822ms/664KiB, 마지막 282행 939ms/374KiB였고 분석 RPC도 1,201ms/189KiB였다. 이 과거 이력과 모델을 기본 패널보다 먼저 기다렸다. 이름 카드 표본은 69ms/4KiB로 주요 대기 경로가 아니었다.

- 기본 권한·명단·라운드 상태를 먼저 표시하고 점수와 모델 Promise는 별도로 전달한다. 점수 초기 미수신은 0점으로 대체하지 않으며 실패는 해당 영역의 안내와 재시도로 처리한다.
- 같은 조건에서 재조회하면 기존 수치를 유지한다. 계정·권한·라운드·단계·현재 공개 점수 스냅샷이 바뀌면 오래된 응답을 적용하지 않는다. 비공개 원본 점수를 클라이언트의 조건 키에 넣지 않는다.
- 경기 진행 중 10명 현재 점수가 완성돼 있으면 과거 전체 점수와 모델을 다시 읽지 않는다. 그 외 과거 이력은 정렬과 전체 범위를 보존하면서 첫 페이지 다음 두 페이지씩 병렬 조회한다. 전체 개수 집계·이력 자르기·서비스 권한으로 조회 우회는 적용하지 않았다.
- 분석 배열을 선수마다 재검색하던 계산은 한 번의 순회로 바꾸고 역할·맵·초기점수 우선순위를 보존했다. 시계의 반복 렌더에서 같은 계산을 재사용한다. 맵 선택/진행 성공 후 서버 재검증과 겹치던 클라이언트 새로고침도 제거했다.

| 관측 상태 | 결과 |
|---|---|
| 변경 전 경기 준비 화면 | 전체 load 4.65초(따뜻한 순회), 8.31초(최초 순회). 점수 조회를 기다리는 구조였다. 초기 모달 표시 시점은 별도로 측정하지 않았다. |

## 남아 있는 서버 지연

변경 후 따뜻한 순회에서도 관리 멤버의 본문은 4.37초(변경 전 0.50초), 통계 2.16초(1.25초), 인증 경유 화면 5.07초(1.57초)로 편차가 컸다. 인증 경유 값에는 도착 페이지까지의 이동이 포함된다. 코드량 감소를 모든 화면의 응답 시간 개선으로 대신 제시하지 않는다.

QA DB가 제공한 누적 지표 두 표본의 서버 시각 차이는 360.43초였다. 평균 CPU 코어별 I/O 대기는 약 12.7%, 주 디스크 I/O 사용 시간은 약 27.5%, 읽기 약 10.64MiB/s·쓰기 약 2.66MiB/s였다. 사용 가능 메모리는 106.84→112.32MiB(제공 총 메모리 433.93MiB)였다. 로컬 호스트는 약 23.2GiB의 메모리가 남아 있었다. DB I/O 대기는 관측 사실이며 이번 수정이 해당 대기의 원인을 전부 설명하거나 해결했다는 근거는 없다. Disk I/O 예산 잔여량·완전한 회복 여부도 확인하지 못했다. [제공 지표 정의](https://supabase.com/docs/guides/observability/metrics)·[연결 안내](https://supabase.com/docs/guides/observability/metrics/vendor-agnostic).

서비스 권한으로 같은 이력을 읽는 비교도 8.70초로 느려 앱에 도입하지 않았다. 정확도를 바꾸는 이력 축소, 계정 간 권한 캐시, 유료 자원 변경은 적용하지 않았다. 후속은 일상 사용에서 남는 느린 요청의 조회 계획·자원 시계열을 대조하는 것이다. 추가 전체 회귀·온라인 QA 부하 반복은 중단한다.

## 재측정 도구

`node scripts/measure-all-pages.mjs <결과명>`은 전체 목록을 기본 두 번 측정한다. `PAGE_MEASURE_RUNS=1`로 횟수를 줄이고 `PAGE_MEASURE_ONLY='진행 중 내전'`으로 한 대상을 제한한다. QA 서버는 기존 실행을 재사용하며 이 도구로 재시작·시드하지 않는다. 측정기는 기존 QA 리더 계정으로 별도 브라우저에 로그인하고 마지막에 그 세션만 해제한다. 원본 JSON은 로컬 산출물로 두고 계정·클랜·경기 식별자 없는 비교 CSV만 저장소에 보관한다.
