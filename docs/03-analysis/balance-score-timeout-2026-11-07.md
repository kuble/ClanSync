# 편성 점수 조회 실패와 멤버 교체의 조회 범위

2026-11-07, `codex/live-session-formation`. 진단·재현 결과이며 제품 조회 구조·DB 함수는 변경하지 않았다.

## 실제 QA 오류

- Management API의 QA API Gateway 로그에서 2026-11-06 **17:26:51.696 / 17:26:54.388 UTC**(11월 7일 02:26 KST)에 `/rest/v1/rpc/read_balance_analysis_model`의 HTTP 500 두 건을 확인했다. 점수 이력 REST 조회 실패는 해당 조회 범위에서 나오지 않았다.
- 같은 구간의 Postgres 로그에 **17:26:59.755 / 17:27:02.498 UTC**, SQLSTATE **57014**, `canceling statement due to statement timeout`이 남았다. 함수 위치는 `private.balance_prediction_basis`의 SELECT 순회와 `private.balance_analysis_bundle` 반환이며 둘 다 `public.read_balance_analysis_model` 호출 경로다. 시간만으로 개별 요청을 일대일 대응하지 않았으며, 이 분석 함수의 실제 시간 초과 발생을 근거로 사용했다.
- QA의 `authenticated`·`authenticator`는 모두 `statement_timeout=8s`이다. 사용자 클랜의 완료 정규 내전 이력은 조회 시점에 1,291건이며 완료 수동 내전은 0건이었다. 원래 화면 캡처의 정확한 발생 시각은 없어 위 두 건과 같은 사건이라고 단정하지 않는다.
- QA와 로컬의 `balance_prediction_basis`·`balance_analysis_bundle`·`read_balance_analysis_model` 함수 본문 MD5가 모두 일치했다. 스키마 버전 차이로 생긴 오류라는 근거는 없다. 개인정보·인증값·원본 SQL 인수는 기록하지 않았다.

## 오류 주입 없는 로컬 재현

전용 `127.0.0.1:55431`의 임시 12인 Premium 클랜·정규 방에서 이력을 생성했다. 각 경기에는 서로 다른 10명·역할·3종 맵·시작/정산 순서를 둔다. 운영진 인증으로 **실제 공개 RPC**를 호출했으며 지연/오류 응답을 주입하거나 기존 8초 제한을 줄이지 않았다. 누적 이력만 늘렸다.

| 완료 이력 | 동시 요청 | 왕복 시간 | 응답 |
|---:|---:|---:|---|
| 100건 | 1 | 44ms | 200 |
| 1,291건 | 1 | 292ms | 200 |
| 1,291건 | 2 | 317ms | 둘 다 200 |
| 5,000건 | 1 | 2,090ms | 200 |
| 10,000건 | 1 | 7,340ms | 200 |
| 10,000건 | 2 | 7,343ms | 둘 다 200 |
| 12,000건 | 1 | **8,015ms** | **500 / 57014** |

- 각 행은 단일 실험 표본이며 동시 요청 행의 시간은 그룹 전체 경과다. [측정 CSV](balance-score-replay-2026-11-07.csv).
- 12,000건에서 **실제 분석 계산이 기존 제한을 초과해 DB가 취소하는 현상**을 재현했다. 이는 오류창 처리 검사에 사용했던 모의 502와 다른 검사다.
- QA와 같은 1,291건은 이 로컬에서 시간 초과가 나지 않았다. QA가 적은 이력에서 8초를 넘긴 당시 CPU·I/O·동시 실행의 기여도는 이 표로 확정할 수 없다. Disk I/O 예산 소진이나 잠금이 직접 원인이라고 주장하지 않는다. 온라인 부하 재현은 하지 않았다.
- 대량 픽스처의 일반 행별 삭제가 시간 제한에 걸려 공식 전용 로컬 스택 정리 절차로 전환했다. 종료 후 계정·클랜·경기는 **각 0건**이다. 사용자 QA·운영 DB는 변경하지 않았다.

## 가득 찬 명단에서 멤버를 교체하면

1. [편집기](../../src/components/main-clan/clan-balance-roster-editor.tsx)는 받은 점수·분석 문맥을 사용해 새 10명 명단과 점수·승률을 화면에서 즉시 계산한다. 최초 계산을 위해 교체 멤버만 따로 요청하지 않는다.
2. 400ms 자동 저장은 [명단 액션](../../src/app/actions/clan-balance-session.ts)의 `updateBalanceRosterAction`에 **10명 전체 명단 JSON·버전**을 보낸다. 전체 참가 가능 목록으로 소속을 검증하고 현재 버전 조건으로 저장한다. 전체 명단 JSON 자체는 작은 데이터다.
3. DB의 `private.refresh_balance_analysis` UPDATE 트리거는 명단 변경 시 클랜 분석 문맥을 만들고 10개 슬롯의 스냅샷을 다시 만든다. 변경한 한 명만 계산하는 경로가 아니다. 초기 티어가 있으면 이 문맥 구성도 `balance_prediction_basis`를 호출한다.
4. 저장 성공 후 `revalidatePath`가 현재 화면을 다시 렌더링한다. [방 로더](../../src/components/main-clan/clan-balance-room-data.tsx)는 전체 참가 가능 목록·현재 경기·선호·투표 등과 [점수 로더](../../src/lib/balance/load-balance-score-data.ts)의 **전체 완료 내전 이력·분석 모델 RPC**를 다시 읽는다. 멤버 프로필의 모든 필드를 읽는다는 뜻은 아니다.
5. [실시간 구독](../../src/components/main-clan/clan-balance-session-realtime.tsx)도 DB 변경 시 전체 `router.refresh`를 요청하고, 보완용 30초 갱신도 수행한다. 동일 조작에서 저장 후 렌더링과 실시간 갱신이 겹칠 수 있다. 이 조사에서 한 교체당 요청 횟수는 별도로 계측하지 않았으므로 고정 횟수를 주장하지 않는다.

## 병목과 적절한 개선 단위

- `balance_prediction_basis`는 과거 경기의 시작·정산 사건을 처음부터 순회하고, 커지는 JSONB 기준값·대기 변경 내역을 갱신한다. 현 구조는 명단 변경과 무관한 이력 재생·전송까지 반복한다.
- 동일 1,291건의 모의 이력을 앱의 실제 계산 함수에 넣은 로컬 Node 측정에서 JS 예측 모델 생성은 **27.38ms**, 이미 받은 모델·점수 문맥으로 1,000번 명단을 바꿔 점수·승률을 계산한 평균은 **0.0159ms/회**였다. 이 값은 UI 렌더링·DB·네트워크를 제외한 계산 비용이며 사용자 기기의 브라우저 지연으로 일반화하지 않는다.
- 우선순위는 **처음 읽은 점수·모델 재사용 → 명단 변경은 화면 계산 → 명단 저장 응답만 반영 → 다른 화면에는 명단 변경만 반영**이다. 이미 읽은 멤버에 대해 교체마다 새 요청을 할 필요는 없다. 아직 없는 멤버/역할 데이터만 필요한 범위로 읽는 것이 적절하다.
- 팀 승률에는 10명 조합·상대가 함께 영향을 주므로 한 명만의 수식 결과로 대체하지 않는다. 기존 모델을 두고 작은 팀 계산을 다시 하는 것이 맞다. 과거 학습을 새로 하는 비용과 구분한다.
- 결과·기록 정정·역할 점수·계정 연결 변경에는 모델을 무효화해야 한다. 로그인/권한/플랜 경계는 계속 검증하며, 새 권한의 응답에 이전 점수를 남기지 않아야 한다. 임의 최근 N경기 절단이나 사용자 간 공용 캐시로 해결하지 않는다. 기존 8초 제한을 높이는 변경도 하지 않았다.

실제 실패 원인은 분석 조회의 DB 시간 초과로 확인했고, 전체 이력 재생의 시간 초과는 로컬에서 재현했다. 아직 명단 저장·실시간 공유·점수 캐시의 제품 구조를 수정한 단계는 아니다.
